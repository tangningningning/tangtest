# adaptive_cache_mec · Python 编码规范

> 适用：新增与修改的 Python 源码、实验脚本和与 Python 代码直接关联的配置接口。目的不是一次性格式化或重构旧代码，而是保证后续变更可读、可追溯、数值与算法合同不被意外改变。
>
> 优先级：用户当前任务明确要求 > 当前项目现行代码/配置中的实际合同 > 本规范的通用建议。冲突必须报告，不要静默选择。

## 1. 最小修改与现有风格
- 修改前只读目标模块和直接相关调用链。沿用该模块现有可读风格；不要为符合本规范而全文件格式化、重命名历史API或清理无关代码。
- 新代码遵循 PEP 8、PEP 257 基本约定；每层尽量保持函数单一职责。若项目已配置 Black/Ruff/isort/类型检查，遵从**现有**配置；不自作主张安装或引入新工具、全库门禁。
- 避免无意义的 wrapper、重复逻辑、隐藏全局状态、长链式隐式副作用。能够复用项目正式入口，就不另写平行实现。
- 不为少量一次性分析增加持久模块；确需临时代码时完成后删除。

## 2. 命名与公开合同
- Python 模块、函数、变量使用 `snake_case`；类使用 `PascalCase`；常量使用 `UPPER_SNAKE_CASE`；布尔量命名表达判断意义，例如 `is_valid`、`has_cache`。
- 对现有跨模块API、配置键、JSON字段及 checkpoint 键，保持原有名称与语义；改名属于合同变更，不因编码美观而顺带进行。
- 数值变量在易混淆时采用明确单位后缀：`distance_m`、`time_s`、`rate_bps`、`bandwidth_hz`、`energy_j`、`cpu_cycles`、`power_w`。不要让 `mb` 同时表示 Mbit 与 MB。
- 使用原生语义名而非 `x1`、`tmp2`、`result_final2`；复杂数学符号可在局部注释给出与论文符号的映射。

## 3. 函数、类型与注释
- 新增或修改的函数，在不会与现有框架或Torch动态对象冲突的情况下补充参数及返回类型标注；不需要为了补全老代码的所有注解而扩大任务。
- 有非显然合同的函数写简短 docstring：用途、输入与输出、单位、可变性、重要边界条件。注释解释“为什么”和数学假设，避免逐行复述代码。
- 公开数值函数应在注释或文档中明确坐标维度、带宽/功率单位、shape约束、是否可微，以及采样/平均/等效值的口径。
- TODO须有具体原因或阻碍；不遗留无上下文的`pass`、空异常捕获或临时debug代码。

## 4. 输入与错误处理
- 在数据/配置入口校验必需字段、shape、单位范围、可行域和文件是否存在；无效值要显式失败并提供足够上下文，不能静默回退到假定默认值。
- 捕获具体异常类型；只有具备明确恢复策略的分支才回退。`except Exception`若用于任务边界记录，必须保留原始异常原因，不得吞错继续产生伪结果。
- 不使用裸 `assert` 作为正式运行时输入校验（生产运行可能禁用assert）；内部不可达条件可以按现有项目惯例处理。
- 不在库函数中随意 `print`；沿用项目既有日志接口。避免在每个Slot/任务热路径输出大量日志。

## 5. 数值计算与物理量
- 在计算前确认输入单位和归一化口径：bit/Mbit/byte、Hz/MHz、W/dBm、cycle/Gcycle、秒/Slot、二维/三维距离；必要时只在接口边界转换。
- 除法、log、exp、softmax、概率和迭代收敛等数值操作，采用与当前数学问题一致的稳定性处理；禁止用任意 epsilon、截断、阈值改变可行域或目标函数而不说明。
- 新增带宽、SINR、信道增益等函数，保持与 `src/common/system_model.py` 等权威实现一致，不复制一套略有差异的公式。
- KKT 的速率函数与导数必须来自同一资源分配与噪声合同；不要为消除异常私自改变可行域、容差或fallback。
- 缺失物理可靠性映射时，正的 Shannon 理论速率只能报告数学可计算性，不能命名成 `reliable_link` 或推断真实成功率。
- 任何数值常量都应复用配置或已存在的命名常量；不可把实验标定值散落硬编码在Trainer里。

## 6. PPO / 多节点策略特别约束
- 明确Tensor/数组维度含义：`[batch, node, candidate]`等示例只在实际 shape 符合时使用；转换、mask与广播处优先注释当前真实shape。
- 必须维护 legal mask、条件策略、action log-prob、联合概率、old/new策略和优势学习的现有一致性；不改变动作Schema、缓存/UAV控制粒度、PPO更新顺序或梯度路径，除非任务明确授权。
- 明确何处需要 `detach`/`no_grad`，不得为了绕过RuntimeError随意切断计算图；避免原地操作破坏梯度；数值处理应兼容实际 dtype/device。
- 随机性应使用现有种子、RNG和训练/评估模式合同；不要新增隐式全局播种或将Training数据混入Validation/Test。
- Checkpoint与模型构造版本必须遵守现行加载合同；不能用 `strict=False`、忽略哈希/维度冲突等方法伪造兼容。

## 7. Matching / KKT / Slot特别约束
- 候选合法性、服务缓存状态、节点资源、边界条件和目标函数应与当前正式实现一致；不要在不同模块分别写一套“近似合法性”判断。
- 任务完成时延与 `independent_per_slot` 的模型含义必须分开：没有跨Slot任务状态时，不能在代码或日志中暗示完成了真实队列服务或1秒硬截止。
- 日志与指标聚合必须区分任务加权、Slot等权、Episode等权及训练/测试指标；报告变量名应表明口径。

## 8. 配置、数据与文件输出
- 读取文件采用项目既有路径解析器、manifest与配置加载器；不要依赖当前shell目录或绝对个人路径（用于文档说明的已知环境解释器除外）。
- 解析 TOML/JSON 时与正式 `project_config` / `validate_for_formal_experiment` 保持一致；新增配置字段时同步真正使用该字段的入口和重复映射。
- 不覆盖正式配置、Training Pool、manifest、Checkpoint、runs或reports中既有成果。独立实验输出使用有意义的阶段名、配置哈希/来源和独立目录。
- 对同一资料的新版本优先使用最近版本；历史数据只在用户明确要求比较时纳入。
- 不自动补新依赖；若确需依赖，先说明用途与风险，等待授权。

## 9. 修改后最低限度验证
- 只执行与修改范围对应的最小必要检查，例如`python -m py_compile <changed.py>`、官方配置加载、单个必要的既有回归测试或极小接口检查。
- 修改KKT/PPO行为时，不可用“语法检查通过”证明数值或训练正确；报告未验证项。没有明确授权，不自动跑全量pytest、完整Episode、Matching/KKT对照或PPO训练。
- 如工具未安装，不为了格式化或静态检查擅自安装。只做可用检查并如实说明。
- 结束时删除本次建立的临时脚本、测试文件及中间文件，不删除既有用户产物。

## 10. 交付说明
- 简洁列出：本次修改文件、修改原因、保留的算法/配置合同、实际执行的检查及结果、没有执行的测试和遗留风险。
- 默认不自动commit或push。
