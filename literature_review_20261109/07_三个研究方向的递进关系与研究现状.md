# 三个研究方向的递进关系与研究现状

## 一、先给结论

三个方向在**文字上**可以形成“配置—迁移—多业务在线”的递进，但在**数学模型上**能否成为三个独立科学问题，取决于是否把边界写清楚。按目前已核查的文献，得到三点判断：

1. **P1 与 P2 不是简单的“P1 加车辆移动”。** P1 的对象是“服务配置/放置 + 任务执行”的跨时间尺度协调；P2 的对象是“运行中的服务实例/状态”随车辆移动更换宿主，并保持活动任务连续。两者可以共享服务放置、节点选择和带宽变量，但 P2 多出“迁移对象、状态同步、迁移窗口、源/目标重叠”的约束。若 P1 已把服务迁移作为配置更新手段（如 TMAGRL），两者的边界必须靠“是否迁移运行状态/是否保持活动任务”来划，而不是靠“是否移动”。
2. **P3 不是简单的“P1/P2 加业务类型和资源变量”。** P3 的对象是“多业务构成/流量/信道变化下的服务部署与带宽/CPU 在线供给”，其核心是长期效用、部署调整成本、队列积压的权衡；P1 的核心是慢/快时间尺度下的配置保持与任务时限可接纳性；P2 的核心是单车移动下的迁移连续性与传输竞争。三者可以共享资源约束，但不能互相替代。
3. **目前最明显的重复风险在 P1 与 P3。** 两者都可能写成“服务部署 + 带宽/CPU + 长期优化”。若 P1 只做“慢层配置、快层执行”，P3 只做“多业务在线部署”，边界尚可；若 P1 也做长期在线、P3 也做配置保持/时限，就会变成同一问题的两种表述。

## 二、三个方向的机制边界

| 维度 | P1 多时间尺度配置—执行 | P2 不完美预测迁移—传输 | P3 多业务非平稳在线协同 |
|---|---|---|---|
| 核心对象 | 服务配置/放置、配置保持时间、任务接纳与执行 | 运行中的服务实例/必要状态、迁移目标/时机 | 多业务服务部署、带宽/CPU供给 |
| 核心不确定性 | 车辆区域分布、服务流行度、任务到达 | 位置预测误差、迁移窗口、链路/目标资源 | 业务构成、任务流量、无线信道 |
| 核心时间结构 | 慢层配置周期/保持时间 vs 快层任务时隙 | 迁移准备/同步/切换窗口 vs 任务执行 | 逐时隙在线决策 vs 长期效用/队列 |
| 核心连续性约束 | 配置变化期间任务能否被接纳并在剩余时限内完成 | 迁移期间源端持续服务、目标就绪、失败回退 | 队列稳定、长期效用、部署调整成本 |
| 典型决策 | 部署哪些服务、保持多久、UAV目标区域/移动、任务接纳/执行节点、带宽/CPU | 是否迁移、何时迁移、迁往何处、迁移带宽、正常任务传输资源 | 部署什么服务、带宽/CPU分配、是否调整部署 |
| 已有直接VEC近邻 | L001、L008、L014、L103、L005（部分） | L003、L029、L069、L087、L094、L041、L118 | L005、L049、L086、L117、L112、L133、L120 |
| 已有通用/UAV近邻 | L084、L134、L037、L048、L002、L067 | L080、L004、L115、L051（方法） | L101、L108、L051 |

## 三、P2 是否只是 P1 加移动性？

**不是，但需要防止写成“P1+迁移动作”。**

支持独立性的证据：
- L029 的迁移对象是 VM 服务宿主，迁移会占用回传带宽、造成 CPU 性能退化，并把迁移流与业务数据放在同一回传容量约束中；这不是 P1 的“配置更新”能覆盖的。
- L087 的迁移对象是容器镜像、内存/增量状态和通信切换，包含预迁移、状态同步、切换/恢复的时序；P1 的服务配置通常只决定“在哪里有哪种服务”，不处理运行状态。
- L080 明确区分服务功能（SF）与用户专属服务实例（SI），迁移包含暂停、状态同步、恢复；P1 的服务放置一般不含用户上下文。
- L004 进一步把“用户专属 SI + 未完成任务 + 剩余时限 + CPU”放在同一模型，说明 P2 的连续性约束可以独立于 P1 的配置周期。

但边界风险：
- L002（TMAGRL）已经把“主动服务副本预部署 + 响应式迁移”放进双时间尺度框架。若 P1 也把“服务迁移”作为慢层配置动作，P1 与 P2 会重叠。
- 若 P2 只做“预测位置→选最近节点→分配带宽”，而 P1 已经做“服务放置+资源分配”，P2 的增量可能只剩“移动性”这个场景标签，不足以独立成点。

**建议边界**：P1 不处理运行状态迁移和活动任务连续性；P2 不重新定义服务配置周期，只把迁移时机/目标/带宽/源端持续服务/回退作为核心。P2 的“迁移窗口”必须是任务时限、链路可用时间、状态同步进度共同决定的，不是“离开RSU前的时间”。

## 四、P3 是否只是 P1/P2 加业务类型和资源变量？

**不是，但“多业务”本身不构成独立贡献。**

支持独立性的证据：
- L005 把紧急任务（ET）与一般任务（GT）的时延/能耗目标分开，使用两级真实队列和 Lyapunov 漂移上界，且把业务比例与总到达分开；这说明“业务构成/流量/信道”可以形成独立的问题结构。
- L049 把三类任务的比例变化、切片激活、带宽/算力重配和重配成本放在双时间尺度 RL 中；这说明“业务比例变化+资源重配”已有直接 VEC 研究。
- L101 把服务程序放置、任务调度、功率/CPU、长期部署预算放在同一在线问题；这说明“服务部署+任务资源+长期约束”不是 P3 独有。
- L086 在 VEC 中做在线服务放置+能耗虚拟队列；这说明“VEC 在线部署”已有直接先例。

但边界风险：
- 若 P3 只是“多业务 + Lyapunov + 服务部署 + 带宽/CPU”，而 P1 已经做“服务部署 + 带宽/CPU + 长期效用”，两者会高度重合。
- 若 P3 不区分“业务构成变化”和“总流量变化”，只是把总到达率做成时变，那么它没有超出 L005/L049 的机制。
- 若 P3 把“切片激活”当成“服务部署”，会与 L049 的对象混淆；切片是逻辑资源，不是服务程序/实例。

**建议边界**：P3 的核心不是“多业务”标签，而是“业务构成变化（需要哪些服务）× 同类任务流量变化（队列负载）× 信道变化（传输能力）”对“服务部署需求—带宽/CPU供给—长期效用/调整成本/积压”的**不同作用路径**。若模型只有聚合总负载，P3 应缩为“在线资源分配”，不宜作为独立创新点。

## 五、已有论文是否同时覆盖多个方向？

| 论文 | 覆盖关系 | 说明 |
|---|---|---|
| L002 TMAGRL | P1+P2 | 主动副本预部署+响应式迁移，双时间尺度；说明 P1/P2 可在同一框架内出现，边界要靠“运行状态/连续性”划 |
| L004 He | P2+剩余时限/CPU | 用户专属 SI、未完成任务、状态同步、CPU；与 P1 的“剩余时限可接纳性”有方法重叠 |
| L005 | P3（+P1部分） | 业务比例、流量、信道、真实队列、在线资源；无服务程序部署 |
| L049 CST-RL | P3（+P2部分） | 任务类型比例、切片重配、双时间尺度；无服务实例迁移 |
| L101 OJSTR | P1+P3 | 服务程序放置、任务调度、功率/CPU、长期预算；非车联网 |
| L086 OPEC | P1/P3 | VEC 在线服务放置+能耗队列；无多业务构成/信道 |
| L087 MAPSM | P2 | 预测+容器预迁移+状态同步；无迁移带宽/窗口联合 |

**没有发现**一篇已核查论文同时覆盖“P1 配置保持—剩余时限可接纳性 + P2 预测误差—迁移窗口—传输竞争 + P3 业务构成/流量/信道分离”的完整组合。这个“没有发现”是本地语料的检索结论，不是领域不存在。

## 六、对三个方向的保留/收缩建议

1. **P1 保留，但收缩**：从“服务部署周期自适应”收缩为“配置保持时间—任务剩余时限—资源可行性”的联合关系，以及快层执行结果如何修正慢层配置。若正式模型不能写出这个关系，P1 应降为“多时间尺度服务部署与卸载”，创新性需重新评估。
2. **P2 保留，但收缩**：从“预测辅助迁移+资源分配”收缩为“预测误差—迁移可用窗口—迁移带宽/正常任务传输竞争”的联合可行性，并明确源端持续服务、目标预分配/状态同步、有条件回退。若目标仍由最近预测节点预先给定、带宽仍是需求参数，P2 与 L029/L080 的差异不足。
3. **P3 保留，但收缩**：从“多业务+Lyapunov在线优化”收缩为“业务构成、同类流量、信道变化对服务部署需求与带宽/CPU供给的不同作用路径”，并明确长期效用、部署调整成本、队列积压的权衡。若模型只有聚合负载，P3 应合并到 P1 或降为在线资源分配。
4. **不建议保留的表述**：部署周期自适应本身；Lyapunov本身；P-DQN本身；轨迹预测+迁移的组合；多业务标签本身；切片激活=服务部署；任务迁移=服务实例迁移。
