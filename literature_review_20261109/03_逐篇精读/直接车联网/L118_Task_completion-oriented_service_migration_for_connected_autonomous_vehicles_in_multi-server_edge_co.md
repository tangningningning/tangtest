## 2 背景/问题/作者思路

【作者原文】CAV 行驶使其到服务边缘服务器的距离增大，通信时延升高；服务迁移即"把 CAV 的服务实例（如虚拟机）迁到更近的边缘服务器"以保障及时卸载与执行，但频繁迁移消耗大量资源。现有服务迁移研究的目标多限于单一指标（时延、能耗或成本），忽略任务紧急度与完成率，也未同时协调迁移能耗、卸载成本、时延与任务关键性。作者并明确指出："多数算法关注迁到哪里，而不是是否应该迁移"（p3、p10 §5.2）。

【作者方案】两阶段 ITOSM：阶段一把执行时间、传输时间、卸载成本用信息熵赋权合成综合得分，按紧急度选服务器（EIT 选最高分、MIT 选次高分以分散负载）；阶段二用改进二值粒子群（BPSO）决定"是否迁移服务实例"。目标为最大化按时完成任务数，受迁移能耗预算与卸载成本预算约束（p1、§4）。

【个人分析】这是四篇中唯一在符号层显式给出"服务实例大小 S_i"与"迁移时间 (λ+S_i)/B"的工作，命名与形式最接近服务实例迁移；但其执行语义仍是"迁移完成后在目标单点执行"，没有源端持续服务、没有执行进度、也没有迁移窗口，因此不能直接充当"无缝/在线迁移"的先例。

## 3 系统模型与对象

1. M 个边缘服务器 ES_j，N 辆 CAV，每车 K 个任务。每 CAV 有专属服务实例 VM_i，**该 CAV 的所有任务都必须由自己的 VM_i 执行**；假设所有服务实例在各 ES 均可用且相互独立（p3 §3.2）。
2. 移动模型：总行驶时间分为等长时隙 τ，相邻位置间隔一个时隙；**任一任务的执行时间不超过 τ**；于是离散轨迹可等价视为任务处理时间线（p4 §3.3）。与 L028 同类，任务在单时隙内完成，模型中不存在跨时隙任务积压。
3. 任务五元组 (λ_i,k, C_i,k, O_i,k, W_i,k, D_i,k)；W∈{1,2,3} 对应 NIT/MIT/EIT；截止期按紧急度取 τ/3、τ/2、τ（p10 §5.1）。
4. 卸载变量 φ_i,j,k∈{0,1}：loc=0 本地、loc=j 在 ES_j 执行；迁移变量 z_i,j′,j,k∈{0,1}：VM_i 从 ES_j′ 迁到 ES_j；执行 v_i,k 时 VM_i 至多驻留一个 ES（p4–5 §3.5）。
5. 迁移时间式(2)：t_m = z·(λ_i,k+S_i)/B + (1−z)·O_i,k/B。**迁移搬运"未执行任务的输入数据 + 服务实例本身"**（p5 原文），B 为 ES 间有线带宽。未迁移时该项不消失，而退化为"结果经有线转发到离车最近的 ES"。
6. 完成时间式(4)：T^m = t_u(j′) + [(1−z)·t_e(j′) + z·t_e(j)] + t_m + t_d。上传指向 VM 当前所在的 j′；若迁移则在 j 执行，否则在 j′ 执行；t_d 为结果无线回传（式(7)）。因此结果回传被拆成"有线转发 + 无线末跳"两段，与 L028 的两跳反馈同构。
7. 计算：ES 总算力 f_j 按同服务器任务数 N_i,j,k 均分（式(6)），即算力份额= f_j/N_i,j,k；不建模过载失效；资源不足时把实例迁到更有余量的 ES（p5 §3.6）。
8. 能耗：只计迁移/转发能耗 E_i,j,k = z(λ+S_i)E_b + (1−z)O_i,k·E_b（式(9)），车辆自身计算与推进能耗不计；总能耗 E_t≤E^b（式(10)）。
9. 成本：按分配算力的单价计费（式(11)(12)），每车 C^t_i≤C^b_i。

## 4 优化问题（目标/变量/约束/式号）

P1（式(14)）：max_{Z,φ} 𝒩 = Σ_iΣ_k H{T_i,k≤D_i,k}（式(13)），约束
C1 车端算力 0≤f_i≤f^max_i；C2 ES 算力 0≤f_j≤f^max_j；C3 Σ_jφ_i,j,k≤1；C4 Σ_j z_i,j′,j,k≤1；C5 E_t≤E^b；C6 C^t_i≤C^b_i。

- 变量：φ（卸载目标）与 z（是否迁移、源 j′、目标 j）。
- 没有迁移窗口约束（不要求迁移在车辆驶出覆盖前完成），没有源端持续服务约束，没有迁移失败/回滚/重试约束。
- 没有带宽或功率分配变量：B、W_j、p_i、h_i,j 均为参数。
- C5/C6 是标量预算上限，不是资源分配决策；它们只截断可行域，不产生"把资源分给谁"的优化。
- **记号冲突**：E_b 同时表示"每比特迁移能耗"（式(9)）与"迁移能耗预算"（式(10)、C5），读者须按上下文区分。

## 5 求解方法

- 阶段一（§4.1，式(15)–(19)、算法1）：对每个任务的候选服务器集合（通信范围内，H∈[2,6]）计算执行时间 q_j1、传输时间 q_j2、卸载成本 q_j3；min-max 归一化（式(15)）→ 概率矩阵（式(16)）→ 信息熵（式(17)）→ 权重（式(18)）→ 综合得分（式(19)）。W=1 直接本地；W=3 选最高分；W=2 选次高分（避免压垮最优服务器）。
- 阶段二（§4.2，式(20)–(31)、算法2）：粒子为 N×K 二值矩阵 X_p，元素 x_i,k 表示"该任务是否迁移服务实例"；适应度式(21) F=Σ(D_i,k−T_i,k)²+ρ(max(0,E_t−E^b)+max(0,Σ(C^t_i−C^b_i)))，ρ=10000，未完成时置 T=0；前期用标准 BPSO 速度-位置更新（式(23)(26)(27)），后期改用去掉惯性项的局部搜索规则（式(28)(29)–(31)）；惯性权重线性递减（式(25)）；违约粒子重生（算法2 第24–26行）。
- 算法3：先由算法1 得卸载决策，再由算法2 得迁移决策，最后统计按时完成数。复杂度 O(PGNK)。
- 结构判断：粒子只编码"是否迁移"，**不编码目标服务器**；迁移目标由阶段一的 φ 决定。这与作者"多数算法只关注迁到哪里"的定位一致，但也意味着"迁移目标选择"本身没有被优化，只是被继承。
- 式(19) 用原始 q_jn 而非归一化 b_jn 加权，而 q 是时延/成本（越小越好），文中却称 s_j 越大越好。若按字面执行，"选最高分"会选到最差服务器。此点须向作者或代码核实。

- 平台：Windows 11、Ryzen 9 7940HX（16 核）、Python 3.12.3 + torch 2.6.0，自建 Python 仿真器（p9）。
- 拓扑：M=40 沿 X 轴密集部署，**覆盖半径 R_es=8 m**，区域 4R_es×2R_es，主服务器周围再随机生成 1–4 个偏移服务器；CAV 用改进随机游走，X 向步长 11–26 m/时隙（τ=5 s），均速约 2.2–5.2 m/s，Y 向 0–2 m 且有 1/3 停止概率（p9–10）。
- 表4 主要参数：N∈{20,30,40,50}、K=10、λ∈[250,700] KB、C∈[120,300] cycles/bit、O∈[100,280] KB、f_j∈{0.1,…,1.0} GHz、f_i∈{0.02,…,0.05} GHz、W_j=1 Mbps、B=4 Mbps、p_i=1 W、h=10⁻³、σ²=10⁻⁹ W、μ=1.5、E^b∈{80,…,240}、C^b_i∈{10,…,50}、H∈[2,6]、P=50、G=100。
- 基线：BPSO、TOSM[40]、RA（随机迁移）、AM（总是迁到最近服务器）。指标：按时完成任务数与 QoS（式(32)，仅对完成任务累加 (D−T)·W）。
- 算例（表5–6，3 ES、1 CAV、3 任务、VM 90 KB）：ITOSM 三任务全成（1.2607/1.9997/4.6800 s），其余四法 EIT 均失败（3.7084 s）；QoS 上 AM 最高（7.0445）但 EIT 失败，ITOSM 为 2.5386，TOSM/BPSO/RA 为 0.9503。
- 表7–10：输入区间 [100,250]→[100,700] 时 ITOSM 完成数 191→127；输出、工作量同向下降；服务器数 40→100 时 185→195；相对提升最高 133.33%。图3–9 为趋势，正文未给逐点数值。
- 量纲自查（阅读者）：(a) 表4 的 W_j=1 Mbps 与式(1) 以带宽（Hz）代入 log 的写法冲突；若按字面 1 Mbps，250 KB 输入上传已约 2.05 s，超过 EIT 的 1.667 s 截止期，与约 95% 的高完成率不相容；若 W_j 实为 1 MHz 且 log₂ 项约 10，则时延量级才合理。(b) 表4 的 E^b 单位写作 GJ（10⁹ J），而算例给"0.008/KB、预算 5.0"，两者相差约 9 个数量级；若按表4 取值，C5 恒不紧。两点均需作者数据核实。

## 7 作者局限

- 结论（p15）：结果来自合成移动模型、OFDMA 与"服务持续可用"假设；真实部署还会遇到异构覆盖与网络拥塞；未来用公开真实 GPS 轨迹与 trace 驱动仿真验证泛化性。
- 明确不建模过载失效（p5 §3.6）；不计 CAV 自身计算与推进能耗（p5 §3.7）。
- 基线选择上自陈"与以往以迁移为中心的方法直接比较意义有限"，故只与 BPSO/TOSM/RA/AM 比（p10 §5.2），这限制了与其它服务迁移工作的可比性。

## 8 阅读者潜在局限（不是作者结论）

1. 迁移对象边界：确有 VM 与服务实例大小 S_i，形式上属服务实例迁移；但迁移发生在**执行之前**（先上传到 j′，再把 VM+未执行输入搬到 j，再在 j 执行）。全程无执行进度、无脏页迭代、无停机时间、无双端并行。"pending task"仅指尚未开始的输入数据。
2. 未完成任务：由于"任一任务执行时间≤τ"且无跨时隙积压，本文不处理"执行到一半再迁移"；也没有任务被丢弃后的重试或回退路径。
3. 源节点持续服务：未建模。迁移期间只有 t_m 的串行等待，没有源端继续处理、没有结果合并、也没有"迁移期间服务不可用"的可用性指标。由式(4) 可直接推出：迁移只有在目标端节省的执行时间超过 t_m 时才有净收益（Δt_e>t_m），这是本文结构决定的，不是作者的论述。
4. 迁移窗口：没有"必须在驶出覆盖前完成迁移"的约束，也没有剩余驻留时间变量；唯一时限是 D_i,k。故不能把本文当作迁移窗口证据。
5. 联合资源：算力按任务数均分、带宽固定、功率固定；无带宽/功率/算力的连续分配，也无迁移流与业务流共享链路的约束。
6. 适应度式(21) 用 (D−T)²：完成得越早惩罚越大，最优解倾向"刚好压线完成"；未完成置 T=0 得 D² 惩罚。这与"最大化完成数"并不等价，是替代性设计。
7. 表4 与算例的量纲不一致，图未做图像核验；表5 的"最终服务器/迁移前服务器"两列与式(4) 的 j′/j 对应关系需逐例复核。

## 10 可复用证据与不能说的话

可复用：
- §2.1 对 task migration 与 service migration 的清晰定义（p2）：前者转移计算任务，后者迁移服务实例以维持服务连续——可直接引用作概念区分；
- 服务实例大小 S_i 进入迁移时间（式(2)）与迁移能耗（式(9)）的写法，可用于论证"实例迁移成本随状态量增长"；
- "先上传到源、再迁移、再在目标执行"的时序（式(4)），可用于说明迁移被串行计入完成时间；
- 迁移能耗预算 C5 与卸载成本预算 C6 的约束形式；
- 表5 的逐任务对照与表6 的 QoS/完成率权衡（AM 高 QoS 但 EIT 失败）。

不能说：
- "该文实现了带脏页/停机的 live migration"——原文无脏页与停机模型；
- "该文处理了未完成任务交接"——任务均在单时隙内完成；
- "该文保证迁移期间服务不中断"——未建模可用性；
- "该文优化了迁移目标"——目标由阶段一给定，粒子只编码是否迁移；
- "该文联合优化了带宽/算力/功率"——均为参数；
- "完成率提升 10%"可作为普适结论——摘要的 10.00% 只对应 EIT 的特定设置，正文表7–10 的相对提升最高 133.33%，口径不同，须分开表述。
