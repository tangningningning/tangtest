# Cache 长期 KEEP 的最小反事实收益验证

## 结论摘要

在 seed 30020、30023 的 Slot 100、200 四个诊断状态中，实际策略均选择 KEEP。每个状态有 351 个合法 UPDATE 候选；本对照只强制执行 UPDATE 组内当前策略评分最高的那个候选，随后恢复同一冻结确定性策略，并从干预Slot评价到Slot 299的完整后缀。

**四个 UPDATE 分支的累计Return均低于对应KEEP分支；没有发现该候选UPDATE优于KEEP的实例，发现 KEEP 优于该候选UPDATE的实例4个。** 这只说明在这两个seed、两个时点、所测试的一个候选上UPDATE较差；不能推断其余合法UPDATE候选或整个Validation集合。

更新均仅改变 `UAV_0` 缓存：服务ID `[5,6,7]` 改为 `[2,5,8]`（移除 6、7，加入 2、8），其他缓存节点不变。UPDATE使观测到的缓存命中增加26–288个、Cloud分配减少26–288个，但同一后缀的任务效用下降、任务时延与车辆能耗上升。新增Cache成本为0.319925，移动成本差为0；任务效用变化与Cache成本精确解释了Return差值。

- 只读取Validation seed 30020、30023 的现有逐Slot环境输入与原始摘要，没有读取Test seed，也没有重跑完整Validation。
- 两个分支从完整基线重放在干预决策前保存的同一深拷贝状态开始，共用同一组确定性逐Slot外生输入。策略及Checkpoint保持冻结；干预后不再强制动作。确定性执行没有额外采样随机性。
- 两个完整基线均与正式Validation的Return、Cache动作路径和UAV动作路径完全一致：seed 30020 Return `3149.9538163485413`，seed 30023 Return `3368.8282081635266`，Return差均为0。

## Cache与任务分配细节

- 原策略在四个干预点均确定性选择KEEP。`p_keep` 为0.705–0.754，`p_update_group` 为0.246–0.295，KEEP始终在组概率比较中胜出。
- 目标UPDATE来自合法候选中UPDATE组的最高原始评分；候选索引依次为 seed30020/Slot100 `251`、Slot200 `251`，seed30023/Slot100 `253`、Slot200 `252`。各状态有351个合法UPDATE候选。
- 四个B分支均只有干预Slot发生实际Cache重配置；之后策略没有再选择UPDATE。A分支整个后缀无实际缓存配置变化。
- seed30020 / Slot100中，UPDATE后实际分配到 `UAV_0` 的任务由559变为700，Cloud由1030降为742，缓存命中由1769增为2057；同时总时延增加14111.534秒，车辆能耗增加680.390 J，任务效用减少365.291。seed30023 / Slot100中 `UAV_0` 分配由541变为576，Cloud由1390降为1310，命中增加80；总时延增加7288.141秒，车辆能耗增加270.893 J，任务效用减少178.147。这表明缓存更新确实改变了后续可行分配与Matching结果，命中增加本身并不保证更高系统收益。

## 对Macro信用分配的判断

**有依据进行定向检查，但尚不能确认存在信用分配问题。** 同一策略评分最高的合法UPDATE候选在四个实测状态下都低于KEEP的实际后缀Return，策略原本选择KEEP与这些观测结果一致；这也可能是合理的KEEP偏好。现有对照只测试每个状态一个UPDATE候选，且仅覆盖两个seed和两个时点，既不能证明UPDATE组整体都差，也不能证明PPO错误估计价值或优势。若继续诊断，优先核对Macro在这类状态中KEEP/UPDATE组的价值或优势估计与实际后缀回报是否一致，再决定是否需要扩大候选对照；本次未执行额外实验。
