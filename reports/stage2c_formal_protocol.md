# Stage2c corrected PPO formal protocol

The split contract is `environment_data/data_split_manifest.json`. Each unit is one complete, sequential 300-slot realization. Train uses seeds 20001–20300, validation uses 30001–30030, and final test uses 40001–40100. The pools are disjoint. The preexisting training pool is preserved; validation and test are generated by `scripts/generation/generate_episode_pool.py` with the same parsed generator settings and independent episode seed streams. Historical slots 0–239 and 240–299 are calibration subsets within training, not held-out evaluation data.

The generator manifest records the config fingerprint and fixed input artifact hashes. `scripts/generation/validate_data_split.py --split both` checks pool completeness, seed and provenance contracts, 300-slot content, finite numeric scenario arrays, and environment loading. It performs an alignment/reset smoke on the first realization of each evaluation split without running the policy or Matching/KKT.

The corrected proposed policy has architecture version 2. Its UAV candidate encoder is a deterministic deep copy of the seeded UAV encoder at construction. The three intended actor learning rates, 1e-4, 5e-4, and 1e-3, must share the same initialization seed and actor/critic initial state hashes. Record these hashes in each training manifest. Stage2b architecture version 1 checkpoints are rejected by formal evaluation; older corrected v2 checkpoints without an explicit version are identified by the full candidate encoder state signature and still loaded strictly.

During the next formal training task, `latest_checkpoint.pt` remains the resume checkpoint. Corrected proposed training also saves `epoch_010_checkpoint.pt` through `epoch_300_checkpoint.pt` every 10 completed epochs using the same checkpoint payload, including model, optimizer, scaling, epoch, global step, and RNG state. `best_train_return_checkpoint.pt` is a training diagnostic only. It cannot be the final selected policy.

After training, evaluate every periodic checkpoint on all 30 validation realizations with `scripts/evaluation/select_validation_checkpoint.py --run-dir <run> --output-dir <validation-output>`. Selection uses mean episode return; approximately tied means choose the earlier epoch. The script writes one metrics row per checkpoint and `validation_selection.json`, including the selected checkpoint SHA256.

`scripts/evaluation/evaluate_policy.py --checkpoint <checkpoint> --split validation --data-root environment_data/proposed_joint_validation --output-dir <output> --deterministic` runs actor-driven sequential evaluation. It writes per-realization JSONL metrics, an evaluation manifest, and an aggregate summary. It creates no optimizer, executes no backward pass, and performs no PPO, Exact-Q teacher, or cache TDQ action selection. It uses frozen training T_ref and E_ref. A test invocation requires `--split test --data-root environment_data/proposed_joint_test --selection-metadata <validation_selection.json>` and the checkpoint path and SHA256 must match that validation selection. Test accepts one selected checkpoint per invocation and performs no model selection.

The selection return is the sum of slot rewards, which is the sum of actual `G(t) = Q(t) - cache_cost(t) - movement_cost(t)`. `mean_G` is its per-slot mean. Per-realization `p95_delay` is the 95th percentile of per-slot mean task delay; the aggregate file also reports the 95th percentile across realization mean delays. These definitions are recorded explicitly because neither is a pooled per-task delay percentile.

Validation and test use the same environment dynamics, task metrics, and split manifest, leaving room for later baselines to reuse these data and metric definitions. This preparation task does not run the formal 300-epoch training or the final 100-realization test.
