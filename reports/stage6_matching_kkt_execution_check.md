## 2. Edge 未被选中的实测原因

对 141 个实际分配到 Cloud 的任务，既有 Matching/KKT 记录给出的互斥分类为：

| Cloud 任务原因 | 数量 | 占 Cloud 任务 |
|---|---:|---:|
| 没有任何 Edge 节点缓存所需服务 | 80 | 56.74% |
| 服务已缓存，但所有缓存节点都没有有效物理/通信路径 | 0 | 0.00% |
| 有物理 Edge 候选但最终选择 Cloud | 61 | 43.26% |

61 个存在 Edge 路径的任务都至少有一个 KKT 可行的单任务转移候选。对它们再按实际保存的评价拆分：

- **33 个**：即使把 Edge 候选放在独占整节点 CPU/带宽的无共享上界，效用也不高于 Cloud 的实际效用。这说明该任务的实际信道、传输与计算综合结果不足以胜过 Cloud；现有记录没有把这 33 个进一步唯一归因于“无线”或“计算”。
- **28 个**：无共享 Edge 上界有潜在优势，但将任务转至 Edge 后对整槽任务重新做 KKT 资源分配，系统效用优势被共享资源和其他任务重分配抵消。记录支持“CPU/带宽资源竞争相关”，但不能把每个案例单独判定为 CPU 竞争或带宽竞争。
- **186 个**合法 Cloud→Edge 单任务转移候选全部没有提升全槽 Task Utility，最佳 ΔQ 为 **-0.006407**，正收益见证为 0。故在这 12 个槽的已评价动作中，没有证据表明 Cloud 任务转 Edge 会提高系统任务效用。

速率记录显示，186 个转移候选里有 181 个 Edge 有效上行速率低于 Cloud 的固定 200 Mbps。但速率不是时延的充分比较：Cloud 上传时延额外乘以系数 15；实际已分配任务中 RSU/UAV_0/UAV_1 的平均通信时延分别为 0.319/0.181/0.612 秒，Cloud 为 0.652 秒。Edge 传输在部分路径更快，然而 UAV 计算时延均值为 1.436–2.221 秒，且车辆发射能耗高于 Cloud。Cloud 的 40 GHz CPU 池在这 12 个状态中均达到 100%；同时 Edge 平均 CPU/带宽份额使用率为 RSU_0 66.67%、RSU_1 33.33%、UAV_0 91.67%、UAV_1 75.00%。这些是资源竞争的实际使用证据，不能据此把 Cloud 选择简单归因于单一资源。

因此本样本的原因排序是：**缓存缺失（80）是最大且可直接确认的原因；其余路径中，33 个的 Cloud 综合效用优于 Edge 无共享上界，28 个潜在优势被 KKT 全槽资源共享抵消；没有“缓存命中但物理链路不可行”的任务。** 仅凭距离或 CPU 配置不能做上述归因；这里的拆分来自既有逐任务候选和 KKT 重分配记录。

## 3. 时延超过 1 秒时的 Slot 语义

该实现没有将 1 秒 Slot 长度当作任务时延上限。`task_utility` 对有限、非负的总时延直接按

`omega_T × (1 - delay / T_ref) + omega_E × (1 - vehicle_energy / E_ref)`

计分；没有 `delay <= 1s` 的拒绝、截断或失败分支。已有实际结果中 Cloud 平均时延 2.317 秒、RSU 1.214 秒、两个 UAV 分别 2.402/2.048 秒，均仍进入 Matching 输出并获得 Task Utility。

Matching 的输入是当前 Slot 的 `actual_tasks`，模块说明其任务逐 Slot 独立完成评价；`execute_slot` 返回本槽任务的匹配、时延、能耗、效用及系统效用，不返回待处理任务队列或跨槽任务状态。**因此当前模型将超过 1 秒的任务仍按本 Slot 独立任务完成记账，不跨 Slot 排队或延续。** 这与代码声明的槽级效用模型一致；若要把它解释成带截止时间、排队和持续服务的真实系统，则缺少相应队列与截止期机制，属于系统建模假设/边界，不能仅凭本代码称为实现错误。

源码位置：`src/decision/task_allocation.py:1-14,1810-1840`、`src/decision/slot_environment.py:332-358,487-662,825-903`、`src/common/system_model.py:90-129,362-386`。

## 结论分类

- **实现错误：未发现。** Matching 对当前槽任务重新计算 KKT 资源分配，槽结果中的实际时延、车辆能耗和效用被保留；没有把超过 1 秒的任务错误丢弃。
- **系统建模假设：明确存在。** 1 秒是任务到达/决策步长，而非硬截止时间；任务按槽独立结算，没有跨槽队列。Cloud 采用 40 GHz 有限共享 CPU 和每任务固定 200 Mbps 等效上行，且不模拟 Cloud 上行争用。
- **实际性能瓶颈：缓存缺失占主导，其次为 Edge 综合效用与资源共享。** 141 个 Cloud 任务中 80 个找不到 Edge 缓存服务；其余存在路径的 Cloud 任务里，33 个 Cloud 胜过 Edge 无共享上界，28 个潜在 Edge 优势在整槽 KKT 资源重分配后消失。Cloud CPU 池虽已饱和，但这 12 槽中没有正收益的 Cloud→Edge 转移见证。

以上结论限于既有 12 个 Training 槽、176 个任务及已保存的候选评价；不外推为完整训练池总体规律。
