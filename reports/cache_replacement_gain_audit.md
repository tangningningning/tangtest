# Cache replacement gain 审计

## 审计结论

在固定 `seed=4401`、连续 50 个 execution slot 的现有 rollout 口径下，共评估 2,864 个可行 add/delete/swap cache 邻居。所有候选的净 replacement gain 都小于 0，因此优化器没有接受任何缓存替换；此前观测到的 `replacement_gain=0` 是“accepted optimizer gain”，不是候选净收益等于 0。

关键结论是：本次不是“正的缓存收益恰好被成本抵消”。候选的预测服务效用增量全部为 0；成本项是候选净收益的唯一负项。虽然有 362 个候选提高了动态缓存覆盖率，但在当前 `predicted_service_utility` 的逐任务最优路径评估中，这些变化没有提高最终 surrogate utility，说明候选服务大多是已有路径的冗余覆盖，或未成为任务的最优执行路径。

本次只使用运行时内存拦截记录候选评估，没有修改算法、配置、reward 或任何 artifact；没有运行 PPO 训练或完整 SUMO 仿真。

## 1. 运行与统计口径

| 项目 | 结果 |
|---|---:|
| 固定 seed | 4401 |
| execution slot | 50（slot 0–49） |
| observation dimension | 154 |
| action dimension | 11 |
| service 数量 | 10 |
| cache trigger 总次数 | 209 |
| 实际 cache change | 0 |
| candidate 总数 | 2,864 |
| candidate 平均数/slot | 57.28 |
| optimizer accepted move | 0 |
| stop reason | 全部 `converged_by_no_improvement` |

候选数量定义为 cache optimizer 在实际触发节点上枚举并评估的可行 add/delete/swap 邻居数量。候选净收益以当前 cache reference state 为基准：

```text
candidate_net_gain
  = candidate_objective - reference_objective
  = utility_gain - service_loading_cost - control_cost - other_penalty
```

`replacement_gain` 则沿用优化器统计口径，即 `final_objective - initial_objective`；由于没有候选满足严格改进条件，该值在每个 slot 都为 0。

## 3. gain 分解与成本审计

当前实现的目标函数为：

```text
objective(C) = predicted_service_utility(C) - cache_update_cost(C_prev, C)
```

缓存更新成本实现为：

```text
loaded_mb       = additions @ service_sizes_mb
loading_energy  = xi_ca * loaded_mb
update_cost     = eta_ca * actual_trigger
                  + lambda_cache * loading_energy
```

对应代码位置：

- `src/decision/cache_configuration.py:872`：candidate objective；
- `src/decision/cache_configuration.py:1012`：add/delete/swap 邻居枚举；
- `src/decision/cache_configuration.py:1336`：只有严格超过当前 objective 加 tolerance 才接受；
- `src/common/system_model.py:226`：加载量、加载能耗和控制成本计算。

2,864 个候选的分解结果满足：

```text
utility_gain = 0
candidate_net_gain
  = -(service_loading_cost + control_cost)
```

`other penalty` 的最大绝对值仅为 `3.22e-15`，所以没有发现未记录的额外惩罚项，也没有发现公式中存在成本重复扣除。成本确实使所有候选更差，但更根本的原因是候选本身没有产生预测服务效用提升，而不是成本抵消了一个正的 utility gain。

## 4. 忽略成本时的理论命中收益

为区分“命中覆盖改善”和“最终 utility 改善”，本审计另外计算了不扣 cache cost 的动态缓存覆盖变化：

- 362/2,864 个候选满足 `delta_hit > 0`；
- 最大 `delta_hit = 0.077906`；
- 全部候选平均 `delta_hit = 0.006453`；
- 但是全部候选 `predicted utility gain = 0`。

这里的 `delta_hit` 是预测事件中“至少一个动态缓存节点含有所请求 service”的折扣覆盖率变化；它不是最终 task utility。最终 utility 对每个任务取 local、cloud 和可用 edge path 的最大效用，因此新增一个已由其他节点覆盖、或不能改善最优路径的 service，只能提高覆盖代理，不能提高 objective 中的 `predicted_service_utility`。

## 7. 无更新原因分类

本次属于 **B：存在 trigger，但没有实际 cache update**。

原因按优先级分为：

1. **候选效用中性**：2,864 个候选的 `predicted utility gain` 全为 0。动态缓存覆盖率偶尔上升，但没有转化为逐任务最优执行效用上升。
2. **任何实际替换都会产生控制成本**：候选邻居与 reference cache 不同，因此至少产生一个变化节点的 `eta_ca`；删除没有加载成本，但仍有控制成本，故最好候选仍为 `-0.1`。
3. **新增服务还可能产生加载成本**：add/swap 候选在控制成本之外，还扣除 `lambda_cache × xi_ca × loaded_mb`，最差候选净收益达到 `-1.536427`。
4. **严格改进门槛**：代码要求候选 objective 超过当前 objective 加 `1e-9` 才接受；所有候选均不满足，因而每次以 `converged_by_no_improvement` 结束。

没有证据表明是无 trigger：50/50 个 slot 都有 cache trigger；也没有证据表明 candidate gain 因未计算或 NaN 变成 0：候选 objective、成本和残差均为 finite，代数分解闭合。
