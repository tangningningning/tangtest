# 第一阶段车辆环境问题核实

## 范围与方法

只读取本地最新源码、Training Episode 20001、20150、20300及正式节点坐标文件。三集均存在，未替换Episode。统计使用每集的 `trajectory.csv`、`vehicle_roles.json`、`episode_manifest.json`、已有 `vehicle_predictions.csv`，并核对可用SUMO需求元数据；没有启动SUMO、重新生成轨迹、Matching/KKT或训练。

分析使用 `C:\software\Anaconda_envs\envs\adaptive_cache_mec\python.exe`（`sys.prefix`确认属于`adaptive_cache_mec`）。预测误差将现有预测按车辆ID和目标时刻与同集轨迹坐标对齐计算；这是离线评价，不是重新生成预测。

## A. 代码已确认的事实

- `src/scenario/sumo_scenario.py` 的场景时间步为1秒、warm-up为100秒、正式时长300秒，仿真结束时刻为400秒。正式step索引是 `[100,400)：Slot 0对应SUMO绝对时间100秒，Slot 299对应399秒。采集轨迹会记录仿真时间1至400秒，额外的末时刻不属于300个正式决策Slot。
- `collect_trajectories` 逐步推进SUMO并读取车辆状态；源码明确不调用 `setRoute/changeTarget/rerouteTraveltime` 等路径控制API。
- 研究车辆筛选要求车辆覆盖全部300个正式step且至少有一条warm-up历史记录。随后按固定种子随机抽25辆研究车，再从中抽5辆SV；选择函数不使用路线、任务或效用排序。
- 车辆预测使用 `vehicle_roles.json` 的 `planned_routes.route_edges` 构建路线几何，再从已有轨迹进行路线坐标映射和名义预测。这与“导航路线已知”的预测假设一致；路线已知本身是建模假设。
- 历史需求来源仅能在Episode 20001核实：其 `sumo_demand.meta.json` 指向 `randomTrips`，记录 network SHA-256为 `30379989…388c7d`、random seed 1026025884、traffic seed 1969414811、出发窗口0–60秒、最小行程距离4000米及2个中间点。该网络哈希与本地 `osm.net.xml.gz` 一致。
- Episode 20150、20300缺少 `sumo_demand.meta.json` 和 `sumo_demand.rou.xml`；其历史来源清单也没有SUMO需求文件哈希。角色文件仍有路线边序列和角色选择种子，但不能据此推断这两集的历史traffic seed或原始路由文件。三个Episode manifest均注明旧Stage6来源缺少历史生成与产物来源证明。

主要源码位置：`src/scenario/sumo_scenario.py:49-76, 529-550, 594-690, 693-791`；`src/scenario/scenario_generator.py:237-270`；`src/scenario/vehicle_prediction.py:358-413, 784-805`；正式时间参数见`configs/proposed/system_config.toml:73-85`。

## B. 真实Training轨迹统计

### 车辆完整性与选择偏差

三集轨迹均覆盖400个1秒时间点（最早1秒、最晚400秒），正式轨迹为时间100–399秒。每集出现60辆车，60辆都具有完整300个正式时隙和至少一条正式区间前记录。角色分配均为25辆研究车、5辆SV、20辆TV、35辆背景车。每集的研究车与SV名单都能用历史`research_selection_seed`和`service_selection_seed`从候选集合精确复现。

| Episode | 被选/未选完整候选的平均速度 (m/s) | 被选/未选的正式区间累计距离差均值 (km) | 被选/未选轨迹持续时间均值 (s) | 研究车warm-up记录数 min/mean/max |
|---|---:|---:|---:|---:|
| 20001 | 10.136 / 10.309 | 3.027 / 3.079 | 369.2 / 369.6 | 40 / 69.2 / 99 |
| 20150 | 10.389 / 10.136 | 3.103 / 3.026 | 371.8 / 367.8 | 43 / 71.8 / 99 |
| 20300 | 10.210 / 10.416 | 3.049 / 3.111 | 370.9 / 368.5 | 41 / 70.9 / 98 |

三集所见车辆没有因完整性规则而被排除；被选与未选车辆的速度、位移差约为±2.5%，且方向随Episode改变。样本中没有明显“只选到长行程车辆”的证据。该结果只描述这三集，不能证明随机Trips车流代表真实城市交通。

### 路线与行驶

将角色文件中的路线边序列映射到本地路网后，25辆研究车的规划路线长度均值分别约为6.09、6.13、6.21公里。Episode 20001的路网哈希可确认；20150和20300因历史SUMO来源文件缺失，路线长度仅是按当前本地路网映射的结果，不能确认其历史路网完全相同。

规划路线序列中重复edge占比均值为10.8%、11.6%、14.0%。但观察到的300秒路段中，将相邻重复road采样折叠后，研究车再次经过已访问road的重复段数中位数在三集中均为0，均值为0.08、0.20、0.56段/车。正式轨迹100–399秒内的累计距离差均值约3.03–3.10公里，端点直线位移均值约0.74–0.88公里；这说明路线有明显绕行/回环几何，但规划路线中重复edge不等同于车辆在正式区间持续绕圈。研究车辆平均约25.5%–26.7%的时间速度不超过0.1 m/s，单车最长连续停车均值约32–34秒。

这些数据能说明SUMO路径和轨迹中的绕行情况，不能单独判断其是否符合真实交通代表性。两集原始路由文件缺失，且没有预先设定“路线重复问题”的阈值或现实路网对照，因此该问题保持未决。

## C. 建模假设与潜在偏差

- 这三集体现固定车辆队列：研究车和背景车都覆盖整个300秒正式区间，背景数稳定为35。它符合“固定研究车队”的数据设计，不是程序错误；它不覆盖正式区间内新车流入或背景车辆离开后的开放交通过程。
- 路线有重复edge与绕行，但实际轨迹没有显示大量road重复段。SUMO路线是否合法与其能否代表真实交通是两件事；缺少两集原始需求文件和外部真实交通基准，不能对后者下结论。
- 研究车运动、SV/TV相对距离及最近SV身份在三个时段都变化，足以说明环境存在动态几何优化机会。它不能替代Cache需求收益、无线链路质量或Matching/KKT分析。

## D. 是否需要修正

对已核实的车辆完整性、车辆选择、背景车数量衰减和动态几何，没有证据要求修改车辆角色、仿真时长、Reward、算法或重新生成SUMO。当前固定队列可作为明确声明的研究抽象保留。

最小的可复核性补充是恢复Episode 20150和20300原始`sumo_demand.meta.json`与`sumo_demand.rou.xml`（若有存档），核验历史traffic seed和路由来源。若无法恢复，就保留“历史来源未核实”标记；重新生成不会恢复原始来源，反而会变更实验轨迹。

## 结论

```ini
SUMO_EXECUTION_CONSISTENT = UNRESOLVED
RESEARCH_VEHICLE_SELECTION_CORRECT = YES
SELECTION_BIAS_SEVERITY = LOW

TRAFFIC_DENSITY_DEGRADATION = NO
ROUTE_REPETITION_PROBLEM = UNRESOLVED
VEHICLE_MOBILITY_VARIATION = SUFFICIENT

PREDICTION_WARMUP_PROBLEM = NO

FIXED_COHORT_MODEL_ACCEPTABLE = YES
SUMO_REGENERATION_REQUIRED = NO

SOURCE_CHANGED = NO
CONFIG_CHANGED = NO
FORMAL_DATA_CHANGED = NO
PPO_TRAINING_EXECUTED = NO
```

`SUMO_EXECUTION_CONSISTENT`为UNRESOLVED的原因是两集历史SUMO需求元数据和原始路由文件缺失；其轨迹时间步与正式300-slot时间合同相符，但不能完全追溯生成输入。`ROUTE_REPETITION_PROBLEM`为UNRESOLVED的原因是可观察到路线edge重复和绕行，却没有预设问题阈值或真实交通对照。没有证据支持为动态几何优化而重建当前SUMO数据。
