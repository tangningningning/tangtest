## 4. CPU 容量与真实任务 cycles 量级

10 个 Episode 共 60,000 个 TV 槽位，其中 41,968 个有到达任务（69.95%），平均每槽 13.99 个任务。到达任务 CPU cycles 均值为 6.125×10⁹，中位数 5.190×10⁹，p90 为 10.682×10⁹，范围 2.275×10⁹–17.490×10⁹。每个 1 秒槽位的总到达计算量均值为 85.68×10⁹ cycles，中位数 83.98×10⁹、p90 110.38×10⁹。

下面将每个任务的 cycles 除以单个节点的完整 CPU 能力，得到**无竞争、独占整台节点、仅计算部分**的参考时延；它不是实际 Matching/KKT 结果。真实多任务分配给单任务的 CPU 份额小于等于 1，计算时延会更长。

| 节点 | CPU | 单任务计算参考时延：均值 / p50 / p90 |
|---|---:|---:|
| TV 或 SV | 1 GHz | 6.12 / 5.19 / 10.68 秒 |
| UAV | 5 GHz | 1.22 / 1.04 / 2.14 秒 |
| RSU | 10 GHz | 0.61 / 0.52 / 1.07 秒 |
| Cloud | 40 GHz 池 | 0.15 / 0.13 / 0.27 秒 |

Edge 总名义 CPU 为 35 GHz（5×SV 1 GHz + 2×RSU 10 GHz + 2×UAV 5 GHz）。若把每槽平均 85.68 Gcycles 的到达量全部放在 Edge，原始计算量约为 Edge 一秒总能力的 2.45 倍；但任务可在 TV 本地或 Cloud 执行，且服务缓存、无线链路和每节点资源份额都会限制可选路径。系统全部 CPU 名义相加为 95 GHz（TV 本地 20 + Edge 35 + Cloud 40），与一槽平均到达量的比较只能作为量级提示，不能等同实际利用率、排队稳定性或超载判定；本检查未求解任务分配。

源码位置：`src/decision/task_allocation.py:1741-1759,1861-1915`、`src/common/system_model.py:90-129`；任务 cycles 来自指定 Episode 的 `tasks.csv`。

## 5. 分类结论

- **实现错误：未发现。** 配置读取映射、位置文件加载校验、服务大小单位和容量比较，以及实际信道计算路径互相一致；评分距离没有被错误当作硬覆盖边界。
- **资源配置限制：存在且具体。** TV 本地 cache 仅能放服务 4；SV 每节点最多 2 类，且初始 Edge cache 缺少 0、2、6；RSU/UAV 虽能单独容纳任何一种服务，分别最多存 4/3 类。TV 到最近固定 RSU/UAV 的典型距离约 617/630 米，距离衰减可能压低链路质量。单任务 cycles 相对 1 GHz SV 和 5 GHz UAV 较大，独占满载的计算部分已常达到约 1–2 秒或更长，多任务共享时更明显。
- **建模假设：不是实现缺陷。** 资源值是仿真基线而非实测硬件参数；距离半径只参与候选评分；Cloud 采用 40 GHz 有限共享 CPU、每任务固定 200 Mbps 等效上行，且不模拟 Cloud 上行竞争。这些设定会影响 Edge/Cloud 比较，但不能单靠静态资源检查断言实际任务会选哪条路径。

**回答：当前 Edge 服务能力可能受到限制，主要来自每节点缓存可容纳种类少、初始 Edge 覆盖不全、SV/UAV 单节点 CPU 相对单任务 cycles 偏小，以及固定 RSU/UAV 布局下多数 TV 与节点相距数百米。距离评分尺度之外仍可通信，故空间分布意味着链路质量风险而非硬性失联；是否造成实际效用损失需要任务分配/物理求解结果，本任务按要求未运行该求解。**
