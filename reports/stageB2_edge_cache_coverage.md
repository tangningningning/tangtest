## 5. Cache UPDATE可行空间

当前候选生成按节点枚举10类服务的二进制目标配置，并过滤容量超限项。每节点非KEEP容量可行目标数为：SV **10**、RSU **56**、UAV **34**，分别低于正式候选上限64。因此在当前10类服务和容量下，候选选择上限不会裁掉任何单节点容量可行目标配置。

Episode 20001 Slot 0通过正式`rollout._cache_candidates()`生成了 **231个候选（KEEP 1个、UPDATE 230个）**：50个SV目标、112个RSU目标、68个UAV目标。各节点全部容量可行的非KEEP目标都进入了PPO候选集。服务0、2、6都存在可行的RSU/UAV目标配置，并且实际出现在该Slot的候选目标中，因此当前机制可以合法加入这些遗漏服务。任一UPDATE针对一个节点，可以在该节点内增加、移除或替换服务；跨节点副本布局调整需由多个后续动作完成，不能在一个候选中同时改多个节点。

从初始副本数看，服务4、5、7、8、9有重复副本；服务1、3各有一份。候选空间允许在节点间逐步改变这些副本的位置。Episode 20001 Slots 0–2中，所有已缓存服务请求都至少有一个可行Edge候选，但这只是小样本。重复副本是否带来必要的近端接入收益、加入服务后是否降低任务时延/能耗或提高净Reward，都必须由同场景Matching/KKT反事实验证；本次没有测量这些结果。

PPO将候选0作为KEEP，其余候选作为UPDATE；当前确定性策略按KEEP与UPDATE组概率质量作组间选择，再在UPDATE组内选候选。候选目标是单节点完整服务集合，不限于单一ADD或DELETE操作。由于所有合法单节点目标均保留，当前诊断没有发现明显的候选剪枝覆盖缺口。

## 6. 结论

- **容量限制：** 当前全网容量可行，且已有一个10/10服务的具体容量布局；证据不支持扩大SV、RSU或UAV缓存容量。
- **初始布局：** 正式初始化稳定覆盖7/10服务，30.367%的Training任务请求了未覆盖服务；全网存在10份额外副本。初始化不优化全网覆盖，也不根据需求预测装缓存。数据支持后续评估覆盖感知初始化，但不证明它能提高净效用或应直接替换正式初始化。
- **可访问性：** 在Episode 20001 Slots 0–2样本中，当前缓存服务请求全部可达至少一个Edge候选；样本中的任务可访问缺口来自服务没有全网副本。更广范围内的局部可访问性仍未确定。
- **动态更新：** 合法更新空间明确存在；所有遗漏服务都能加入RSU/UAV，候选集合覆盖了当前每个节点的全部容量可行单节点目标。空间可行不等于更新有正效用。

### 卸载路径和无收益原因

- **UPDATE-0：** Slot 0的一个服务0任务有Edge候选并被分配到Edge；Slot 1的两个服务0任务均有Edge候选，其中一个进入Edge；Slot 2的两个服务0任务均有Edge候选且都进入Edge。Slot 2的Edge总数由1增至2、Cloud由15降至14，但Task Utility仍比KEEP低0.015388，平均时延由2.194261秒升至2.200503秒，车辆能耗由0.150105 J升至0.252953 J。Slot 0–1也出现服务0 Edge替换原有Edge分配，Task Utility分别下降0.018113和0.006949。因此Edge任务数量增加不必然提升任务效用或改善时延/能耗；本例还有0.252043的初始Cache成本。
- **UPDATE-2：** Slot 0–1没有服务2请求，Slot 0 Task Utility与KEEP相同，净损失全为更新成本。Slot 1移除UAV_0上的服务8后，服务8的Edge执行从1降为0，Edge总数从3降为2，Cloud从11升为12，Task Utility下降0.045875。Slot 2有2个服务2请求，二者都有Edge候选，Matching将其中1个放到Edge；但它替代了KEEP下的1个服务8 Edge任务，Edge总数和Cloud总数均未变，Task Utility下降0.004552。链路候选存在，但这一代表性缓存替换没有产生任务效用收益。
- **UPDATE-6：** Slot 0–1没有服务6请求，实际Matching和Task Utility与KEEP相同。Slot 2出现4个服务6请求，4个任务均有RSU_1 Edge候选，但Matching最终仍将4个都分配给Cloud；最终分配和Task Utility与KEEP完全相同。因此本例不能把无任务效用变化归因于服务需求缺失或通信候选缺失。现有选定Matching结果不足以区分Cloud个体效用比较和共享资源影响；不能据此进一步断定具体原因。净Reward差恰好等于Cache成本。

### Episode 20002：独立Training Slot 0

服务2是未覆盖服务中预测Popularity最高者。该Slot有5个服务2任务，全部有UAV_0 Edge候选，但Matching仍将5个分配给Cloud。KEEP和UPDATE的实际执行节点分配、Task Utility、平均时延（2.199224秒）及车辆能耗（0.361957 J）完全相同；更新成本为0.181282，故UPDATE的ΔReward为**-0.181282**。这说明该Slot中无净收益不是因为没有服务2请求或没有Edge通信候选；现有单次Matching/KKT结果不能进一步证明Cloud选择是由哪一项边际效用或共享资源条件主导。

### Matching/KKT与Reward核对

Episode 20001的四分支12个Slot执行和Episode 20002的2个Slot执行均通过正式`execute_configured_slot()`。每次任务都进入合法Edge或Cloud节点；使用Edge的任务对应服务均在该节点缓存。全部KKT求解有限且收敛，最大资源残差为 **9.991×10⁻¹³**；每节点CPU与带宽分配份额不超过1，Cloud CPU用量不超过40 GHz。全部Task Utility、成本、Reward、时延和能耗均为有限数。双UAV全程STAY，移动成本为0。

逐槽核对正式恒等式 `G = Q - C_cache - C_UAV`，14个记录均一致；Update分支的Cache成本只计入Slot 0一次，Slot 1–2成本为0，没有重复扣费。为从完整执行结果提取逐服务记录，Episode 20001四分支三槽按相同输入又确定性复现了一次；复现数值与首轮一致。总计26次正式Slot执行（其中12次为该记录复现）；未对230个UPDATE候选做Matching/KKT穷举。

### 判断与边界

### 当前项目Macro / SMDP信用分配

- `prediction.vehicle.horizon=5`；每个Macro观测含当前Cache、UAV位置、逐车5步预测位置、逐服务5步GRU `rho_pred`、有效horizon mask及time-to-go。候选经济特征也只消费最多5步的预测场景。
- Cache Macro最短/最长Holding为1/5 Slot。每个Macro frame开始选一次Cache；同一frame内Cache保持，UAV由Micro策略每Slot决策；frame结束后下一Macro再生成当前状态下的合法候选和Observation。
- 对frame内Slot `j`，rollout累加 `gamma^j * G(t+j)`，记录实际duration。配置`gamma=1.0`，所以目前frame Reward就是该Holding内Slot Reward求和，Cache更新成本只在真实支付的Slot出现一次。
- Macro Actor优势来自`compute_macro_smdp_gae`：TD残差跨下一个frame bootstrap，递归项为`(gamma*gae_lambda)^duration`；配置`gae_lambda=0.95`，因此跨Macro传播会按经历的Slot数衰减，但不会在5槽边界被截断。若连续4个5槽frame，GAE递归权重约为`0.95^20=0.358`，仍非零。Episode终止时不bootstrap。
- Macro Critic当前目标是`two_step_smdp_td`：本frame Reward、下一frame Reward，再bootstrap到之后的状态价值（临近终止时按终止规则截断）。它是状态价值`V(s)`，不是单独Cache候选的动作价值`Q(s,a)`。
- 另有`Long-Value Critic`以完整实现回报到当前的realized return-to-go作为目标，但它使用独立参数/优化器，代码检查禁止产生Actor/Macro Critic梯度；Macro Actor仍只用SMDP-GAE优势。因此完整回报监督存在，但没有直接进入Cache Actor优势。
- Cache log-prob与当前Macro frame内所有Termination log-prob相加形成joint log-prob；Actor用同一Macro优势及一个joint PPO clipped ratio更新。因此Cache与Termination**共享优势、联合log probability与clip**。这一结构可能把“是否保留缓存”和“是否结束Holding、重新获得决策机会”的信用混在一起，值得验证；仅凭共享本身还不能认定它导致B2-5差异。

核对位置：`rollout.py` 的`_cache_candidates`、frame Reward及`compute_macro_smdp_gae`；`trainer.py` 的`_update_macro`与`_update_long_value_critic_only`；`macro_targets.py` 的两步目标；`policy.py` 的joint log-prob；正式值来自`system_config.toml`。

### Cache候选特征能表达什么

当前正式候选特征为181维缓存状态/目标/差分基础特征，加19维经济特征（合计200维）：

- Macro Observation本身带逐服务、逐horizon的GRU流行度，逐车5步预测位置及当前全节点Cache矩阵；候选目标与差分能指出具体加入/移除哪些服务。
- 19维经济特征显式包含目标节点ID/类型、`log_cache_cost`、装入/释放容量比例、全网副本多样性变化，以及按5个预测步、经节点预测可服务性加权的新增/移除需求总量。
- 因此新增服务6需求和被替换服务5/9需求并非完全缺失；目标Cache差分给出服务身份，状态给出服务级Popularity，经济特征给出添加/删除的预测需求和成本。特征里没有逐服务的独立预测价值标量，添加/删除需求在经济向量中分别聚合；目标缓存容量只体现为装入/释放比例和实际成本。
- 这些值是预测/几何服务性代理，没有针对每个候选的正式KKT资源重分配、Cloud/Edge竞争、实际Task Utility变化或剩余副本的精确区域覆盖价值。全网Cache矩阵使网络可以看到服务5/9仍有其他副本，但不能直接得出RSU_1删除后的精确反事实效用。

判定：`CACHE_OPPORTUNITY_COST_FEATURES=PARTIAL`。现有输入能表示“加什么、删什么、预测需求大致多少、成本多少”，但不能精确表达服务级长期净价值；当前数据也不足以把差异归结为纯粹的网络输入缺失。

### 决策

1. 当前机制已经有跨Macro周期的信用通路：duration-aware SMDP-GAE递归和下一状态价值bootstrap均跨越frame；`gamma=1`且最多5槽Holding不构成“看不到20槽收益”的硬边界。与此同时，GAE按Slot数以`lambda=0.95`衰减，Macro Critic只用两步SMDP TD目标，Long-Value的全回报拟合又没有反馈Actor；故长时差异存在学习难度，但不是完全没有长期信号。
2. 当前5槽预测可用于近期服务需求比较和替换风险提示，不能单独评估100槽缓存更新价值。新增服务6与被删服务5/9必须联合看，不能只看新增服务预测排名。
3. 不足以支持新增专用Cache长期价值估计或立即修改Macro Actor；也不足以支持改变Holding上限或初始化。B2-5只有三个固定动作Training样本，正负差异可被预测需求部分解释，但仍受节点覆盖和Matching/KKT路径影响。
4. Cache与Termination共享优势是结构性信用分配风险，值得下一步做定向对照；但当前未证明它导致了观测到的更新亏损。建议先做一个预先固定规则的小规模预测驱动更新时间对照（仍用同一UPDATE-6和这三个Training Episode，成本按实际计一次），比较预测增删需求与正式KKT净收益；若预测对候选差值已有解释力、但闭环策略仍系统性撤销有利更新，再单独验证共享优势/两步Critic信用路径。暂不改变PPO、Holding或初始化。

### Stage B2-7A：Cloud Fallback Model Decision

#### 论文文字与数学约束

核对对象为 Liu et al. 的 arXiv v2全文（与指定IEEE论文同题；第III-A、III-C、III-F节）。[论文原文](https://arxiv.org/html/2307.09691v2)

| 位置 | 论文写法 | 对Cloud后备的含义 |
|---|---|---|
| III-A 网络架构 | 关联ES可执行；若该ES缺服务，可转发到缓存该服务的协作ES；若没有协作ES缓存所需服务，则交由Cloud。 | 文字描述支持Cloud是“无Edge缓存副本时”的后备。 |
| III-C Case 2–3 | 关联ES或协作ES执行，要求相应服务已缓存；协作ES还要求资源足够。 | 对Edge执行有缓存与资源条件。 |
| III-C Case 4 | 明确写成“任一ES都未缓存该服务时，只能交给Cloud”。 | 文字没有明确覆盖“服务有缓存但当槽资源不足”的处理细节。 |
| III-F 数学问题 | 目标最大化长期QoS总和并扣Cache切换成本；(17c)要求每个任务恰选一个节点，节点集合含ES、Local、Cloud；(17a)、(17d–f)约束缓存及CPU/带宽容量，(17g–h)约束时延和能耗上限。 | 公式没有给出“只要存在可行Edge就禁止Cloud”的条件，例如没有 `d_v,C <= 1 - I[存在可行Edge]`。所以严格后备规则没有被数学约束明确写出。 |

因此，论文的后备说法是系统模型文字，不应误报成优化问题已经施加的硬约束。论文确有Delay/Energy硬QoS上限，但那与Cloud门控条件是两件不同的约束。

#### 当前正式代码路径

正式配置 `algorithm.matching.cloud_fallback_mode="RESOURCE_AWARE_FALLBACK"`（`configs/proposed/system_config.toml:506`）；`slot_environment.py`将配置传给正式Matching（`src/decision/slot_environment.py:503–514`）。

- 对每个任务，`build_feasible_targets()`先检查Edge节点是否缓存该服务；正式调用还要求当前车辆和节点坐标有效、节点角色可识别、CPU与带宽为正、信道增益和计算出的上行速率为正。满足条件的Edge节点才加入该任务的Edge候选（`src/decision/task_allocation.py:229–300, 1784–1824`）。这里没有距离硬阈值；判定使用实际链路模型算出的正速率。
- 在正式`RESOURCE_AWARE_FALLBACK`模式下，候选集合是“所有上述合法Edge + Cloud”。所以Cloud对每个任务始终是候选；存在可行Edge不会屏蔽Cloud。初始映射先取候选表第一项，之后Transfer-Exchange以KKT完整评估后的任务效用和 `sum_v Q_v` 做改进；只有在效用容差内平局时才偏向较少Cloud（`task_allocation.py:293–300, 783, 1189–1287`）。这不是Edge优先约束，也不是全局最优性证明。
- CPU、带宽由KKT按同一Edge节点上的任务联合分配，并检查节点资源份额总和与最小份额；有限Cloud CPU池也作为联合约束（`task_allocation.py:896–942, 2299–2940`）。因此单任务存在Edge候选不能替代整组Matching/KKT的资源可行检查。多个任务会争用CPU/带宽并改变各自时延与效用；若完整联合分配违反资源约束或KKT不可行，该候选Matching会被拒绝。
- 当前代码没有Delay/Energy硬QoS阈值检查。`system_model.task_utility()`把时延和车辆能耗按参考值归一化后作为连续效用（`src/common/system_model.py:341–367`）；参考值不是接纳/拒绝门限。当前配置最小CPU/带宽份额为 `1e-6`，注释称每槽最多9个任务，单靠最小份额不会让这种规模超出单位资源预算。对当前模型，资源竞争主要可降低Task Utility；不能据此声称存在QoS门限造成的Edge不可行。此次只读检查没有评估具体Slot的联合可行性。
- `LEGACY_EDGE_GATE`只在某个任务完全没有合法Edge候选时才给它Cloud；它按任务屏蔽Cloud，没有执行整批任务的Edge-only可行性检查。正式配置当前没有使用该模式，因此它不能直接代表经全局资源验证的严格后备规则。

源码位置：`src/decision/task_allocation.py`（候选与Matching/KKT可行性）、`src/decision/slot_environment.py`（正式传参）、`src/common/system_model.py`（Task Utility）；配置模式由`src/common/project_config.py`校验。

#### 两种规则的数学定义

令 `E_v(t)` 为任务 `v` 在当前Cache和链路状态下的合法Edge集合，`x_vn` 表示执行节点选择，`r` 表示CPU/带宽分配。

| 规则 | 定义 | 研究假设与取舍 |
|---|---|---|
| **A：Cloud与Edge自由竞争** | 每个任务允许 `n in E_v(t) or n=C`，满足每任务唯一分配、Edge缓存/链路、KKT共享资源及Cloud容量约束；选择使 `sum_v Q_v(x,r)` 最大的分配。完整系统仍按 `G=sum_v Q_v-C_cache-C_UAV` 评价。 | 假设Cloud是随时可比较的远程执行选项。最直接对应当前时延/能耗效用目标与正式代码。 |
| **B：Edge优先，Cloud仅作全局后备** | 先构造完整任务集的Edge-only联合可行集 `F_E(t)`：所有任务均分配到 `E_v(t)`，且存在一组满足共享CPU/带宽和明确QoS条件的资源分配。若 `F_E(t)`非空，只在其中优化 `sum Q_v`，令所有Cloud变量为0；若为空，则在Edge/Cloud联合可行解中先最大化Edge执行任务数，再在该最大值下最大化 `sum Q_v`，Cloud只承接全局资源条件下无法留在Edge的任务。 | 把“Cloud是后备”落实成系统优先级。更接近论文III-A/III-C文字，但增加明确的Edge优先级；它可能牺牲Delay/Energy效用。 |

规则B的“Edge可执行”必须看整批任务与资源分配，不能因为每个任务单独存在缓存/链路候选就永久屏蔽Cloud。论文的(17g–h)给出QoS阈值形式；本项目目前没有对应的硬阈值。如果规则B把“无法完成”定义为QoS不达标，必须先指定项目的时延/能耗门限及其任务完成语义。若仅以KKT资源可行作为条件，则正CPU/带宽和极小最小份额下Edge-only解可能很容易成立，Cloud会被系统性排除，即使Cloud的Task Utility更高。

#### 建议、对B2结果的影响与修改边界

当前研究目标是直接优化时延/车辆能耗效用，并在系统Reward中扣Cache和UAV成本，故**目标函数和已有实验更支持规则A**。规则B更贴近论文文字所说的后备语义，但论文数学问题并未明确实施该Cloud门控。为避免仅为提高Edge执行率或UPDATE收益而改变竞争规则，现阶段建议先保留A作为已评估基线；是否转为B属于需要定稿的系统模型选择，故本报告不擅自切换。

B2-1至B2-6的数值均来自当前A模式。B2-3检查的9个Cloud→Edge单任务强制转移为负效用差，是A下的反事实证据；若采用B，某些转移可能因全局Edge优先而变成实际分配，Cache UPDATE的Task Utility、净收益、排序和回本结论都可能改变。Cache成本公式不会因此自动改变，但先前的收益数值不能当成B模式结果，方向和幅度需要在模型定稿后重新评价。

## Stage B2-7B：Prediction-Guided Cache Update Timing

### 固定规则与执行方式

- 使用Training Episode 20004、20005、20006的Slot 0–99；每个Episode分别运行KEEP、Slot 0固定UPDATE-6、预测触发UPDATE-6三条独立分支。三个分支都从同一Episode正式初始Cache/UAV状态复制，使用相同真实任务、轨迹和预测输入；双UAV保持STAY。每次Slot调用正式`execute_configured_slot()`、Transfer-Exchange Matching、KKT及Reward。
- 冻结预测规则：在Slot 0、5、…、95读取当前时点可见的5步GRU popularity，计算`D_s(t)=0.7×20×Σ[h=0..4]ρ̂_s(t+h|t)`，并令`score=D_6-D_5-D_9`。若尚未更新且`score>0`，才尝试目标`RSU_1:{5,7,9}→{6,7}`；执行前通过正式Cache候选接口按当前状态检查目标是否在该节点候选集内。最多更新一次，之后锁定配置。实际未来任务只作为该Slot执行输入，不参与当时决策。

## Stage B2-8：Candidate-Level Predictive Cache Value

### 范围与正式特征

本实验只使用 Training Episode 20007、20008、20009 的 Slot 0–99。每集先通过正式 Rollout 候选接口生成 Slot 0 的 Cache 候选；每集均有 230 个合法 UPDATE（另加 KEEP），但只对冻结规则选出的两个不同候选运行 Matching/KKT。每个 UPDATE 只在 Slot 0 执行一次，之后保持缓存配置；UAV 全程 STAY。共执行 KEEP/A/B 九条分支、900 个正式 Slot，车辆任务、轨迹和系统参数按 Episode 内配对。

正式候选特征为 181 维基础特征加 19 维经济特征。基础特征包含当前/目标 Cache 矩阵及变化；经济特征包含节点与角色、`log_cache_cost`、装入/释放比例、副本多样性变化，以及候选新增和移除服务对应的五个预测时距需求值。需求特征来自预测场景的任务到达/服务分布，经节点预测可服务性加权，并按任务车辆数归一化；它们是预测可服务请求代理，不是 Task Utility 或 Matching/KKT 预测。完整 Cache 矩阵可用于计算全网副本数；候选特征没有直接给出各任务在共享 CPU/带宽下的边际效用，也不提供“预测请求数→净收益”的映射。因此本实验没有把预测需求与成本相减，也不把预测分数称为预测净效用。

实际结果出来前冻结的排序规则：

- **A：** 对每个正式可见 UPDATE，最大化 `Σ demand_added_h0..h4 − Σ demand_removed_h0..h4`。两项使用相同的预测需求代理单位；分数并列时依次选较低 `log_cache_cost`、较低节点索引、目标服务位向量字典序较小的候选。
- **B：** 按字典序最大化新增的“当前全网无副本”服务数；最小化被移除服务中“该节点是最后一个全网副本”的数量；最小化候选节点五步预测移除需求总和；最大化新增需求总和；最后依次以较低 `log_cache_cost`、较低节点索引和目标位向量打破并列。这样区分删除当前节点副本与消灭全网最后副本。成本只用于并列排序。
