# 独立并行任务B：缓存分布与有效更新空间分析

## 结论摘要

- 两个 seed 均有 5 个 SV、2 个 RSU、2 个 UAV 缓存节点。没有节点达到数值上的 100% 占用；但Episode初始状态9/9节点的剩余空间都不足以再放入任何一个缺失服务。到Slot 100/200决策前，仍有6/9节点不能直接加服务，另外3/9可直接加服务。
- 9/9节点都存在容量可行的非KEEP目标。基准轨迹在每个Slot记录的Cache候选数均为352；冻结策略在Slot 100和200选择KEEP，说明这两个状态不是因为候选空间为空。
- 基准Cache在两个seed中都于前5个Slot各执行一次UPDATE，之后到Slot 299保持不变。Slot 100和200决策前的缓存状态相同。
- 初始状态有9/10种服务的全局覆盖，15个超出首副本的重复缓存；前5次更新后全局只剩7/10种服务，服务1出现6个副本。按service_catalog.json静态Popularity加权的全局“至少一份缓存”覆盖代理从90.75%降至77.09%。这不是车辆可达范围内的预测覆盖率，也不是决策时刻需求预测。
- 当前留存的prediction_scenarios.npz和vehicle_predictions.csv不属于3C2的两个seed：文件车辆ID与轨迹中的SV ID不匹配。因此不能可靠计算seed/Slot配对的预测需求覆盖、预测边际增益/损失、可达范围内重复，或识别高预测需求但缺少Edge缓存候选的服务。

## 数据来源与统计口径

- 读取Stage3B配置configs/proposed/stage3_cloud_finite_60ghz.toml、服务目录data/generated/service_catalog.json，以及指定的3C2 Slot JSONL和Markdown。
- JSONL元数据规定每个节点一个整数bitmask，bit位置对应service_ids顺序。初始状态由Slot 0的更新前后bitmask和该Slot的added/removed清单逆向还原；Slot 100和200决策前状态分别取Slot 99和199结束状态。逐项结果显示两个决策前状态一致。
- 已用容量 = 当前节点缓存服务的program_size之和；剩余容量 = 节点容量 − 已用容量；利用率 = 已用 / 容量。可直接新增的服务是“当前未缓存且其大小不超过剩余空间”的服务。
- “数值满”表示利用率达到100%；“直接新增受阻”表示剩余容量不能容纳任一个缺失服务。合法UPDATE允许替换已有服务，所以两者都不等于“没有合法更新”。
- 为核对空间，按当前10个服务的大小枚举了所有容量可行的二进制缓存组合；这是容量可行目标数量，不等于PPO实际可选候选数。实际宏候选数另从3C2轨迹读取。

## 重复、副本和全局服务覆盖

“额外副本”定义为全局服务副本数之和减去已覆盖的不同服务数。静态Popularity覆盖代理按“至少一个缓存节点持有服务”求和，不考虑车辆位置、Edge候选门控、资源竞争或时刻预测。

## 决策时刻预测覆盖与UPDATE候选

当前留存的data/generated/prediction_scenarios.npz含300个origin、20个场景、5个预测horizon，但其metadata的车辆ID以23、87、43、75、58等开头，scenario_seed为20260820。3C2轨迹记录的SV ID为Seed 30020的28、21、30、19、38，Seed 30023的58、7、11、51、31；vehicle_predictions.csv同样属于前述不匹配的生成数据。轨迹JSONL本身只保存缓存状态、实际任务分配/命中汇总、UAV位置和候选数，不保存每个seed在Slot 100/200的预测场景张量。不能将当前生成数据硬套到3C2状态，也不能用实际未来任务替代预测。

源码中的预测候选评价依赖场景中的arrival、service_id、positions_xy：predicted_vehicle_service_demand_by_horizon()按预测场景、预测horizon及折扣构造车辆-服务需求；node_specific_predicted_demand()再按预测位置到节点的可服务性加权；目标配置生成据该节点需求和副本数量构造提案。由于seed对齐的预测张量缺失，本次无法可靠给出：

- 车辆可达范围内的有效重复和预测需求覆盖率；
- 高预测需求但没有合法Edge候选的服务；
- 新增与删除各服务的预测边际覆盖增益/损失；
- 哪个节点具有正的预测更新价值。

已能确认的是容量和候选空间：每节点都非空且有合法替换；容量限制下每个SV/RSU/UAV节点分别有19/293/136个非KEEP可行二进制目标（仅按容量穷举，不等于正式候选提案）。实际3C2轨迹在Slot 100和200均记录352个宏Cache候选，而该Slot没有UPDATE。基准策略每个seed只在Slot 0–4执行5次UPDATE，之后295个决策保持KEEP。

## 必须回答的问题

1. **缓存节点是否普遍已满？** 数值意义上否，0个节点正好达到100%。但初始9/9直接新增受阻；Slot 100/200有6/9受阻。
2. **是否仍可合法替换服务？** 是。所有节点当前非空，源码的has_legal_cache_target_configuration()对非空合法缓存返回有替代目标；每节点容量可行的不同目标也远多于零，Slot 100/200宏候选数为352。
3. **是否覆盖主要预测需求？** UNDETERMINED。可计算的90.75%/77.09%仅为基于静态目录Popularity、全局“至少一副本”的代理，不能代表预测需求有效覆盖。
4. **哪些重复有价值，哪些低效？** 按目录静态权重，服务7、9、5的重复可能有价值，服务1六份可能是低效重复候选；但车辆可达范围未知，不能定性实际收益。
5. **是否存在高预测需求且未覆盖的服务？** UNDETERMINED。Slot 100/200缺失服务0、2、3，但这些只是全局缓存缺失，预测需求权重与Edge候选合法性无法从当前对齐数据确认。
6. **是否有能改善预测覆盖的UPDATE？** 容量可行UPDATE存在，且实际宏候选不为空；预测边际覆盖改善为UNDETERMINED。
7. **长期KEEP是否由初始缓存分布较好造成？** UNDETERMINED。初始状态由均匀随机顺序按容量装入，不按Popularity/预测定制；基准随后在Slot 0–4改了缓存，并将全局静态Popularity覆盖代理从90.75%降到77.09%。Slot 100/200仍有352个候选却选择KEEP，因此KEEP不是“初始状态完全未变”或“没有动作空间”；是否因后续状态与预测需求适配，现有留存数据不能证明。
