# Cache 与 UAV 决策有效性分析

日期：2026-10-10  
范围：仅分析现有 `1e-3` 确定性 Validation（seed 30001–30030，每个环境300 Slot）及同 seed 的 `proposed_joint_validation` 环境输入。不读取 Test seeds，不启动仿真，不改动当前运行中的 Validation。

## 摘要

- 30个 Validation 环境都在 Slot 0、5、10、15 选择并实际执行 Cache UPDATE；Slot 20–299 的56次宏决策全部选择 KEEP。每环境实际配置更新率为4/60个宏决策，即6.67%；按300个Slot计的 `cache_change_rate` 为4/300，即1.33%。
- 跨seed先合并请求后计算，Slot 0–19与280–299的TVD仅0.028；这会掩盖单环境差异。逐seed计算实际请求概率后，基准窗口到后续窗口的TVD均值为0.153，每seed最大基准TVD均值为0.233、最大0.332。跨seed汇总的“小变化”不能代表每个seed内的需求变化小。
- Slot 15后，所选缓存配置的摘要ID在各 seed 内保持不变，且后续平均 `p_keep=0.9547`，范围0.9249–0.9635。日志能确认配置不再变化，不能把摘要ID还原成被缓存的服务ID。
- UAV1在全部9,000条动作记录中选择STAY，目标坐标均为`(5179.650, 1710.410)`。现有结果没有任务到节点分配、UAV分项CPU利用率或按节点任务效用，因此不能判断UAV1是否仍承接任务，也不能判断其算力利用率高低。
- 没有证据证明缓存覆盖率已明显下降或UAV1资源闲置，也没有发现可由现有记录确认的实现错误。当前需要的是配对消融证据，不是立即修改策略或系统。

### 2.2 单seed服务分布与时间变化

对每个seed、每个20-Slot窗口单独计算10维实际请求概率向量：`p[s,w,i] = 窗口内service i的arrival=1任务数 / 该窗口arrival=1任务总数`。`tasks.csv`逐seed、逐窗口的service计数与`popularity.csv`的`request_count`完全一致（0项不一致）。同时对`rho_star`按seed与窗口汇总并归一化，作为Popularity文件中的服务概率轮廓；实际请求频率与它会有有限样本差异。

TVD定义为`0.5 * sum_i |p_i - q_i|`。对每个seed分别计算Slot 0–19与每一个后续窗口的TVD，以及相邻窗口之间的TVD；下表的均值、中位数、分位数均先对seed级指标计算，未先合并seed。

### 2.3 实际Cache动作与配置

每个 seed 的60条Cache宏动作记录完全一致：在 Slot 0、5、10、15 选择UPDATE，其余 Slot 20、25、…、295 均选择KEEP。每环境：

- KEEP：56/60（93.33%）；实际重配置：4次/60个宏决策（6.67%）。
- `cache_change_rate`：4/300 Slot（1.33%）。这个指标是实际配置变更计数除以Slot数，不是缓存未命中率。
- Slot 20–99、100–199、200–299的KEEP概率均值分别约0.9551、0.9548、0.9544；后Slot决策的单次`p_keep`范围为0.9249–0.9635。概率仍随状态有小幅变化，但始终位于KEEP的Argmax一侧。
- 记录到的最终配置摘要在Slot 15后对每个seed保持不变。30个seed的最终配置摘要共有12种，说明seed间最终配置并不唯一；摘要日志没有缓存向量到具体service ID的映射。

环境的`tv_local_cache.json`描述的是预生成的TV本地缓存，不是上述策略选择的Cache配置：这些TV初始只缓存service 4。不能用它替代策略Cache的服务清单。

### 2.4 覆盖率、命中与效用

逐seed结果显示多个环境中的实际请求分布相对Slot 0–19有明显变化（例如最大基准TVD超过0.26的seed），而Slot 20–299的策略配置摘要始终不变。这确认了“请求分布改变但Cache保持不变”同时发生；TVD只描述请求构成变化，本身不能证明变化后的请求未被缓存，也不能证明缓存覆盖恶化。

现有摘要没有策略缓存的service ID清单、服务覆盖率、命中/未命中计数、按服务的卸载节点、按Cache决策时点的任务效用。`total_q`（实际任务效用）、`total_return`和`total_cache_cost`只是每个episode聚合值，无法判断某次KEEP或UPDATE对应了何种服务覆盖及任务结果。因此：

- “Slot 15后配置不再更新”：`SUPPORTED`。
- “单个seed后期请求构成与Slot 0–19不同”：`SUPPORTED`；实测请求概率的seed级平均基准TVD为0.1534、每seed最大TVD均值为0.2328。`rho_star`概率轮廓的变化更小（每seed相邻窗口TVD均值0.0276），实测请求波动还包含抽样差异。
- “长期KEEP导致明显服务覆盖下降/命中恶化”：`INSUFFICIENT_EVIDENCE`。
- “这些早期更新或长期KEEP带来更高/更低收益”：`INSUFFICIENT_EVIDENCE`，没有反事实对照。

## 3. UAV1动作与资源利用

在30个环境共9,000条逐Slot UAV记录中：

| 对象 | 记录结果 |
|---|---|
| UAV0 | MOVE 8,996次，STAY 4次；目标位置/候选来源逐Slot有变化 |
| UAV1 | STAY 9,000次，MOVE 0次；目标位置始终为`(5179.650, 1710.410)`，候选来源始终是`stay` |
| 联合动作 | MOVE/STAY 8,996次（99.956%）；STAY/STAY 4次（0.044%）；其他组合为0 |

UAV1虽在动作组上完全固定，但日志记录的平均STAY组概率约0.5937（30个seed范围0.5917–0.5976），说明确定性Argmax可在中等偏好下产生全程STAY；这只描述动作选择，不表示任务收益或利用率。

每个seed的`total_tasks`与环境`tasks.csv`的真实到达任务数一致，平均约4,208个/episode（范围4,132–4,302）。但这些是全系统任务输入，不是分配到UAV0/UAV1的完成数。Validation汇总没有按UAV的接收任务数、卸载比例、CPU周期/利用率、队列或节点级任务效用；`mean_vehicle_energy_j`也不是UAV CPU利用率。因此不能判断：

- UAV1承接了多少任务或占多少卸载份额；
- UAV1是否长期没有被选择执行任务；
- UAV1固定STAY时是有效服务还是资源低利用。

结论：UAV1动作组与位置均缺乏变化为`SUPPORTED`；UAV1是否闲置或固定部署是否有害为`INSUFFICIENT_EVIDENCE`。

## 4. 下一步实验建议

### 优先级1：完成四组统一Validation后，做Cache更新机制配对消融

建议将`1e-3`当前策略作为参照，在同一组环境seed上比较当前“Slot 15后KEEP”行为与一个明确的后期UPDATE候选/触发方案。现有证据足以说明它值得检验：早期配置更新后，许多seed的实际请求分布与初始窗口相比有实质变化，而策略持续保持同一配置；`rho_star`轮廓变化和实测请求样本噪声也需分开考量。实验仍应检验更新能否改善结果，不能预设更新有益。

至少比较配对Return、`total_q`、缓存成本及更新次数。若要回答“服务覆盖/命中是否下降”，必须在评价结果中能直接读出策略Cache服务清单与请求命中；当前数据没有这些字段，不能靠KEEP率或Cache成本代替。

### 优先级2：UAV1固定部署与动态移动对照

这是一个合理的次级实验问题，因为30个seed中UAV1动作与目标位置完全固定。但现有证据不能说明UAV1低利用或动态移动会更好。对照应使用相同环境seed，并比较总Return/任务效用、两架UAV各自的任务数与计算负载、时延/能耗和移动成本。若无法取得按UAV的任务分配与负载结果，这个对照只能回答系统总目标变化，不能回答“UAV1是否实际服务”。

### Reward敏感度

当前汇总保存了总任务效用、Cache成本、UAV移动成本和Return，却没有按动作或节点拆分的奖励/收益贡献。它不足以证明环境奖励是否对Cache/UAV动作有足够敏感度，也不足以支持调Reward。进行上述配对消融时应同时检查已有奖励分项是否随干预产生可解释的变化；在此之前不修改Reward或策略。

## 5. 明确回答

1. **为什么Cache只在前20 Slot更新？** 确定性Cache选择在Slot 0、5、10、15四次选择UPDATE，随后KEEP概率一直高于0.9249，确定性Argmax持续落在KEEP侧。现有日志支持这是当前状态下的策略动作集中；不能据此断定是代码错误、缓存失效或错误收益判断。
2. **后期是否有需求变化但Cache不更新？** 有，而且跨seed聚合的2.77%低估了单环境变化：实测请求分布相对Slot 0–19的后续窗口TVD，seed级均值为0.1534、每seed最大TVD均值为0.2328，最大为0.3322；例如seed 30020、30023、30013在较大变化组内仍全程KEEP。`rho_star`轮廓的变化较小，且没有缓存命中或反事实收益证据，因此不能仅凭需求TVD判定应更新或认定长期KEEP造成覆盖下降。
3. **UAV1固定STAY时是否仍有效参与任务卸载？** 现有数据无法判断。只能确认其9,000次STAY及固定坐标；没有UAV1任务分配或CPU利用率记录。
4. **是否发现需要立即处理的系统或算法问题？** 没有发现可由这些数据确认的实现故障或已证实的覆盖/利用率损失。Cache长期KEEP与UAV1固定部署是值得验证的策略现象，不是已证实的问题。
5. **四组Validation完成后优先做什么？** 优先进行同seed Cache更新机制配对消融，并以Return、实际任务效用和缓存成本作为已可得的结果；如需解释服务覆盖/命中，先确认评价输出是否能直接给出这两个量。UAV1固定/动态部署对照排在其后，且须记录或读取按UAV的任务负载结果。
