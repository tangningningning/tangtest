# 任务效用归一化尺度核查

## 范围与数据身份

本报告只核对正式任务效用源码、唯一正式配置 `configs/proposed/alternating_actor_updates_v1.toml` 和 `reports/node_level_cost_counterfactual_pilot.md`。没有运行训练、评价或新实验。

试点报告记录 raw 配置 SHA-256 `a2286e45c7be8bb724ce91aeaebe48e0ec518e0a43610ae264b98e7859936bfa`，成本合同 `node_level_cost_upper_bounds_v1`。20 个配对状态来自训练池 Episode seed 20001；任务、轨迹等外生输入原先按历史 `system_config.toml` 生成，但四个分支均按当前正式配置和执行代码重新计算 Matching/KKT、任务效用与成本。因此下述数值是当前合同在一个历史训练池 Episode 的 20 个状态上的即时配对重算，不是多 Episode 总体分布，也不是完整当前配置评价。

## 正式效用公式与执行路径

`src/common/system_model.py::task_utility`（第 547 行起）实际执行：

```text
q_v(t) = omega_T * (1 - T_v(t) / T_ref)
       + omega_E * (1 - E_v_veh(t) / E_ref)
```

当前有效配置为 `omega_T = omega_E = 0.5`、`T_ref = 10,640,415 s`、`E_ref = 95,772.59112 J`。源码函数没有单独的 `a_v(t)` 乘子，也不截断单任务效用；正式任务通过 `load_actual_tasks` 按 `arrival == 1` 进入任务集合，每个已到达任务参与 Matching。

`src/decision/task_allocation.py` 为每个实际匹配任务计算 `per_task_utility`，并在精确评估中求和；`src/decision/slot_environment.py` 将 `matching.task_utility_sum` 作为 `Q(t)`，即：

```text
Q(t) = sum_{v in 本时隙实际匹配任务} q_v(t)
```

这是任务效用总和，不是任务均值。`G(t)` 由 `slot_environment.py` 按 `Q - cache_cost - movement_cost` 计算；两项成本字段已含相应 beta。试点中平均每 Slot 约 14.5 个任务，`Q` 约 14.5，和“每个任务效用接近 1 后求和”一致，没有证据显示把总和错误地记录成均值。

**时延口径。** `system_model.py::edge_execution` 对新建/上传中的边缘任务计算上传时延加计算时延：`D/(q R_i) + L/(alpha_i F_r)`。`task_allocation.py` 对已进入计算/网络延迟阶段的边缘任务计入剩余网络延迟和剩余计算时延。Cloud 路径按 `psi_c * D/(q R_i) + L/f_i` 计算，并在 `NETWORK_DELAY` 阶段加 `remaining_network_delay_s`；当前配置 `psi_c = 17.0`。实现中没有另行计算排队等待或结果回传时延。当前生成器装载的任务默认 `execution_stage=NEW`、`transmit_time_share=1`、剩余网络延迟为零。

**车辆能耗口径。** 对需要上传的边缘任务，`edge_execution` 的上传能耗为 `P_tx * D/(qR_i)`，调用方乘回 `q` 后得到 `P_tx * D/R_i`；Cloud 任务同样按基础无线 airtime 计算 `P_tx * D/R_i`，Cloud 的 `psi_c` 只放大时延，不放大能耗。处于计算/网络延迟阶段的边缘任务能耗设为零。故 `E_v_veh` 仅包括车辆上行发射能耗，不含本地计算能耗、边缘/Cloud 计算能耗或其他设备能耗。

Matching 与 KKT 使用同一任务效用：Cache 状态改变任务可匹配的边缘节点集合，UAV 位置改变空地信道与传输速率；两者都会触发匹配和资源分配变化，再改变每任务的 `T_v`、`E_v_veh` 和 `q_v`。KKT 系数也直接包含 `omega_T/T_ref`、`omega_E/E_ref`（Cloud 上行时延系数再乘 `psi_c`），所以参考尺度会影响实际分配，而不只是输出的 Q 数值。

## 当前参考值及其依据

配置第 371–383 行将两个值说明为固定系统级保守上界，并明确不是训练集 P95。其推导依赖任务输入上限、计算量上限和 KKT 最小资源份额：

- `D_max = 1000 KB * 8000 bit/KB * (1 + 0.20) = 9.6e6 bit`。
- `L_max = 1000 cycle/bit * D_max * (1 + 0.10) = 10.56e9 cycle`。
- `min_cpu_fraction = min_bandwidth_fraction = 1e-6`。KKT 求解器将资源份额下限裁在该 epsilon；因此这些界是基于仿真分配下限的算法/配置界，不是 QoS 服务承诺或实测物理保障。

| 路径/量 | 配置依据 | 推导 | 结果 |
|---|---|---|---:|
| SV 最坏时延路径 | `F_min = 1 GHz * 1e-6 = 1,000 cycle/s`；配置注释给出的边界最小地面速率约 `119.381 bit/s` | `10.56e9/1,000 + 9.6e6/119.3807` | `10,640,415 s` |
| Cloud 时延路径（含 `psi_c=17`） | `R_min = 20 Mbps * 1e-6 = 20 bit/s`；`f_min = 20 GHz * 1e-6 = 20,000 cycle/s` | `17*9.6e6/20 + 10.56e9/20,000` | `8,688,000 s` |
| Cloud 上行能耗上界 | `P_tx=0.1995262315 W`；同一 `D_max` 和 `R_min=20 bit/s` | `P_tx * D_max/R_min`（psi 只用于时延） | `95,772.59112 J` |

配置注释称最大时延路径为 SV，故 `T_ref=10,640,415 s`；`E_ref=95,772.59112 J` 是由 Cloud 最小分配速率给出的上界。前者约 123.2 天。两者都因 `1e-6` 的 KKT 下限而远大于普通 Slot 任务尺度；它们是固定可行域保守上界的推导值，不是任务截止时间或能耗预算。已检查的正式任务配置/`Task` 模型未发现任务 deadline 或能耗 budget 字段，因而没有可直接代入的 QoS 参考尺度。

## 试点中的时延尺度与效用敏感度

试点报告给出的 20 状态均值：KEEP+STAY 时任务平均时延 `18.4544 s`、`Q=14.49997`；REPLACE+STAY 时 `16.3532 s`、`Q` 的配对增量均值 `3.022951e-6`。平均时延减少 `2.101141 s`，Edge 分配比例增加 `4.81` 个百分点（这是实际分配到 SV/RSU/UAV 的比例，不等价于逐任务缓存命中率）。

| 量 | 当前上界归一化下的数值 |
|---|---:|
| KEEP 平均时延 / `T_ref` | `1.73437e-6` |
| REPLACE 平均时延 / `T_ref` | `1.53689e-6` |
| `2.101141 s` 改善 / `T_ref` | `1.97468e-7` |
| 每任务时延效用斜率 `omega_T/T_ref` | `4.69906e-8 utility/s` |
| 该时延改善对应的单任务时延项增益 | `9.87340e-8 utility` |

按平均 `14.5` 个任务/Slot，把该平均时延改善近似施加给每个任务，时延项约贡献 `1.432e-6 Q/Slot`；这是数量级估算，不是逐任务重算。它约为观察到 `3.023e-6` Q 增量的 47%。未保存的任务能耗变化、各 Slot 任务数与平均时延的协方差都会影响精确分解，因此不能把差额直接归因于能耗或实现错误。

若仅作敏感性示例，把 pilot KEEP 平均时延 `18.4544 s` 当作一个“典型尺度”分母，则 `2.101141 s` 对应约 `0.05693` 单任务时延效用增益；按 14.5 个任务同幅变化则约 `0.825 Q/Slot`。该尺度来自单 Episode、20 Slot 的均值，不是 QoS 阈值或总体分位数，**不能据此直接替换正式参考值**。当前有效试点没有 delay P50/P95，也没有足以估计总体典型尺度的多 Episode 样本。

## 能耗证据与敏感性

试点报告没有逐任务 `per_task_vehicle_energy_j`、任务 ID 对应能耗、或配对能耗变化。执行结果结构虽在内存中提供逐任务能耗，但该试点 Markdown 未保存它；现有试点无法给出实际能耗均值、分位数或 Cache REPLACE 的能耗效用贡献。故不能从这份报告推导一个经验 `E_ref`。

可从源码公式给出不依赖能耗样本的宽松关系：对于 `q<=1`、`psi_c>=1` 的上传任务，`E_v_veh <= P_tx*T_v`；计算/网络延迟阶段能耗为零。将该界用于试点报告的平均时延，仅得到平均能耗上界约 `3.682 J/任务`（KEEP）和 `3.263 J/任务`（REPLACE），相应 `E/E_ref` 上界约 `3.845e-5`、`3.407e-5`。这不是实测能耗分布；由于时延还包括计算时间且 Cloud `psi_c=17` 只放大时延，实际值可能显著低于该界。

当前 `omega_E/E_ref = 5.22070e-6 utility/J/任务`。因此每任务 1 J 能耗差在效用中的影响为 `5.22e-6`；若差值汇总跨 14.5 个任务，则量级为 `7.57e-5 Q`。这是公式灵敏度，不代表试点观察到 1 J 差值。此前旧运行记录中的约 `5.157 J` 参考值属于不同奖励/配置合同，不能当作当前试点的实测能耗或当前 `E_ref` 候选。

## 根因判断与证据强度

1. **时延参考尺度过大：证据强。** 当前平均时延只有 `T_ref` 的约 `1.5–1.7 ppm`，2.10 秒变化只有参考值的 `0.197 ppm`。按当前 `omega_T`，每秒只改变约 `4.70e-8` 单任务效用。由此产生的微小 Q 增益与试点结果同量级，说明巨大参考值是“时延改善明显、Q 变化极小”的主要且可量化解释。该界实质上由极小 KKT epsilon 保证，而非服务质量目标。
2. **Cache 候选收益有限：不能据此判定。** 所选 20 个配对状态中 Edge 分配增加 4.81 pp、平均时延减少 2.101 s，表明该候选在这些状态有即时服务改善；但只有一个训练池 Episode、每状态一个候选，无法代表策略访问分布或其他候选。试点每 Slot 平均 Cache 扣费为 `0.0893767`，远大于 `3.02e-6` 的边际 Q 增益；当前奖励下净效用变差主要体现成本项与任务效用边际尺度不匹配，不能单凭试点断言权重应改。
3. **能耗尺度过大：有强烈迹象，但缺直接样本。** `E_ref` 是基于 `20 bit/s` KKT epsilon 下限的 `95.8 kJ` 上界；即使使用试点时延推得的宽松平均能耗上界也低于约 `3.7 J/任务`。这表明分母相对该运行尺度可能过大；然而试点没有实际能耗数据，不能量化其真实归一化项或收益贡献。
4. **效用计算/日志聚合实现问题：目前无直接证据。** 源码按每任务公式求和并把和作为 Q，配置引用读取一致，Slot 级 G 又单独扣除成本。试点报告的 Q 与任务数规模也相符。由于报告缺逐任务能耗和逐 Slot 原始效用分解，仍不能完成每个状态的 `ΔQ = -omega_T*Δsum(T)/T_ref - omega_E*Δsum(E)/E_ref` 数值闭合；这属于观测字段不足，尚不能排除报告聚合口径造成的小幅差异。

## 是否调整及最小后续方案

**需要重新校准参考尺度的证据充分，但现有材料不足以给出可直接采用的新数值。** 不应把单 Episode 均值 `18.4544 s` 或旧合同 `5.157 J` 直接写为正式分母。若研究目标是反映服务质量，优先采用有外部依据的任务截止时间/能耗预算；当前未找到此类正式约束。若暂时没有 QoS 合同，可预先声明使用训练集统计参考：在多个训练 Episode/seed、固定基线策略或明确的全候选基准上保存逐任务时延和车辆能耗，按预先约定的 P90/P95 取固定参考值；将结果写入正式配置并纳入语义哈希/奖励合同。参考值一经确定，应跨 Slot、策略和验证/测试集固定，不得在线更新，也不得用验证/测试结果调参。

最小补证是从配对分支持久化 `task_id`、实际执行目标、`T_v`、`E_v_veh`、单任务效用及每 Slot 求和前后的原始分项，再以多个训练 Episode 建立时延/能耗分布；之后用冻结的候选参考值做离线公式敏感性比较。当前不建议据这 20 个状态直接改参数或权重，也不据此启动训练。
